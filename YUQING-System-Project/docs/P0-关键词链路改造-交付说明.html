一、结论先说

改造前，业务同事手写的词表（如 (辽宁|沈阳|…)+(药监局|药品|…)）在系统里只被当成一个普通字符串：类型、分类、组合表达式、匹配策略全部被丢弃， 采集引擎只取「第一个词」去检索，于是出现 任务显示成功、一键采集跑完、入库 0 条、且日志里没有任何错误。

本次把这条链路打通，并顺手修掉 3 个此前未被发现的真实缺陷。现在：

  • 组合表达式被正确解析为「检索词组 + 本地校验组 + 排除组」，检索请求量 = 主题词个数，不是笛卡尔积；
  • 排除词以「任务级降噪」方式生效，不会误杀其他任务的舆情；
  • 表达式语法错误在录入时就用带列号的提示拦住，不再等到采集完才发现是 0 条；
  • 词表可整份导入（PC 对话框或 SQL），重复导入幂等。

二、四项 P0 交付内容

P0-1 关键词生效改造（核心）

关键词库 → 采集引擎的契约从「拼字符串」升级为「结构化规格」。

改造点改造前改造后
关键词装载 loadKeywords() 只 select keyword_text buildMatcher(taskId) 装载全部字段，类型 / 分类 / 表达式 / 任务级策略一并进入规格
检索词填充 firstKeyword() 只取第一个词，fillUrl 把整串表达式 URL 编码进 wd= searchTerms() 取表达式最后一组，逐词请求；每个词独立预算配额
本地过滤 无（搜索引擎返回什么就入什么） 入库前按「所有组 AND 命中、排除组未命中」过滤，过滤发生在去重之前，不占用去重配额
可观测 入库 0 条无任何信号 CollectResult 新增 filteredCount / isAllFiltered()，单独打点且不计入异常告警（全被过滤属于正常业务结果）
为什么不做笛卡尔积展开：样例1 有 16 个地区词 × 6 个主题词 = 96 次请求。若按 16×6 发起，绝大多数渠道会被限流直接拒绝。 因此采用「主题词检索 + 地区本地校验」：请求量 6 次，地区命中在本地判定，结果等价而成本降低 16 倍。 max-search-terms-per-unit 默认 8，超出自动截断并告警。

P0-2 组合表达式校验器

KeywordExpression.validate() 返回带列位置的错误说明（对外经 GET /yuqing/collect/keyword/validate）， 对应 dev-specs/F-002 验收标准 3。PC 关键词表单在表达式输入框下方实时提示，合法的显示绿色「表达式语法正确」。

容错项说明
全角标点（）｜＋－，、； 与全角空格自动归一化（1:1 映射，报错列号仍与原文对齐）
多余外层括号((东北|…)+(东北超|…)) 整段被包住时自动剥离，不再误报「不支持嵌套括号」
冒号前缀标题药监监测:(辽宁|沈阳)+(药监局|药品) 的标题自动剥离并写进备注
裸 OR 组药监局|药品监管（不带括号）同样识别为组合表达式

真正非法的写法仍然拒绝并给出列号，例如 ((A|B)+(C|D))+(E|F)（首括号中途闭合）、-(广告|代理)（只有排除词、缺检索组）、以 + 结尾。

P0-3 任务级降噪

keyword_type=negative 的关键词，经 yq_task_keyword 关联后只对绑定任务生效。 排除词命中优先级高于任何正向命中（命中即丢弃）。

为什么全局降噪规则 yq_noise_rule 默认不参与采集：该表没有 task_id 维度， 一旦全局启用，「招聘」「代理」这类词会把「某药企被查」之类的高价值舆情一起杀掉。因此 apply-global-noise=false（默认），深度降噪归 F-006 净化去重环节。

P0-4 词表导入工具

把业务同事手写的词表文本一次转成库里的记录，无需逐条手工录入。

五、过程中发现并修掉的 8 个真实缺陷

全部由「脚本实测 / 单测执行」暴露，不是代码走查猜出来的。其中 D1–D4 若不修，系统会静默给出「成功但空」的结果。

#缺陷后果修法
D1 样例2 ((东北|…)+(…)) 整段被外层括号包住，解析器判「不支持嵌套括号」 业务真实词表根本无法导入，一张也进不去 解析前剥离整段冗余外层括号；置空格而非删除，保证报错列号仍与原文对齐
D2 剥离括号后归一化结果残留前后空格（' (东北|…)+(…) '） keyword_text 脏数据，去重失效、列表展示异常 parse 前 trim()，归一化结果再次 trim()
D3 splitWords 在行内先做了去重 「跳过重复 N 条」永远是 0，重复数据被静默吃掉、无从发现 拆词阶段不去重，重复判定与计数统一交给 register()
D4 样例:(A|B)+(C|D) 的冒号标题被当作表达式内容 撞「左括号缺少配对」，业务习惯写法直接报错 新增 stripLeadingLabel()；仅当冒号右侧确实像表达式时才剥离（时间:12:30 不受影响）
D5 30 个前端 types.ts 都写 import type { PageQuery } from '@/api/types'，但该符号并不存在 40 个 TS2305 + 大量 pageNum/pageSize 报错，vue-tsc 失去把关能力 PageQuery 实为 src/types/global.d.ts 的全局环境接口 → 删除 import
D6 VO 接口无条件追加 createTime，而 4 张表的字段清单里已有同名字段 8 个 TS2300 Duplicate identifier 字段清单已含 createTime 时不再补
D7 生成器无条件输出 loadForeignOptions();，但无关联字段的表不生成该函数 3 个 TS2304 Cannot find name 新增 pcForeignBootstrap()，无关联字段则不输出调用
D8 导入对话框 typeTag() 声明返回 string，而 el-tag 的 type 仅接受 5 个字面量 1 个 TS2322 声明 TagType 联合类型
另外记一条流程教训：本项目的 gen-yuqing-collect.mjs 尾部有 4 个大段由 part11a~d.js 合并而来。本次曾两次「直接改生成器里的这段代码」，随后合并脚本用旧版 part 文件把修改静默覆盖回去， 表现为部署报告 ~0 覆盖（什么都没变），极具迷惑性。现在的合并脚本会在每段头部写明来源、 并在合并后自检关键符号（stripLeadingLabel / validateKeywordExpression 等）是否存在，缺失就报错退出。

-- 采集一轮后看是否有「被过滤」信号（而非一片空白）
SELECT task_id, channel_id, fetch_count, insert_count, filtered_count
  FROM yq_collect_log ORDER BY create_time DESC LIMIT 20;
若 fetch_count > 0 而 insert_count = 0 且 filtered_count ≈ fetch_count， 说明链路是通的——只是这一轮抓到的内容都被地区组 / 排除词过滤掉了，属正常业务结果，系统不会误报异常。

八、安全基线

风险处理
越权 三个新接口全部 @SaCheckPermission；导入仅写「关键词库 + 任务关联」两张表，不触碰用户 / 角色 / 菜单； 任务 ID 会校验存在性，避免写到不存在的任务上
SQL 注入 全部走 MyBatis-Plus LambdaQueryWrapper，无字符串拼接，无 ${}；生成 SQL 中的单引号做 '' 转义
脏数据 / 静默失败 解析出错整份拒绝写入；超长表达式报错而非截断；入参长度 512KB 上限 + 条目 5000 条上限 + 行 20000 行上限
DoS（正则回溯） 排除词默认按普通字符串匹配；若启用正则，ExcludeRule.risky() 会扫描 (a+)+ 这类灾难性回溯模式并自动降级为关键词匹配
XSS 关键词文本为纯数据，前端由 Vue 模板自动转义；导入预览表格不使用 v-html
误杀舆情 全局降噪默认关闭（无任务维度）；排除词必须显式绑定任务才生效
