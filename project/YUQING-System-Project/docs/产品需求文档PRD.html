11. 项目概述

1.1 项目背景

当前舆情工作依赖人工搜舆情、人工研判、人工汇总、人工推送、人工写报，五个环节彼此割裂，存在四类结构性痛点：

痛点具体表现后果
漏监靠人工在不同平台间切换检索，覆盖渠道有限、时段不连续突发舆情发现滞后，错过处置黄金时间
误判依赖关键词匹配与个人经验，无法识别隐性舆情、变体表述研判口径不一致，漏判误判并存
迟报研判结论靠导出、转发、群里喊，触达链路长高风险信息到不了决策人手上
重复劳动同源转发被反复统计，日报月报靠手工拼接数据口径失真，报告耗时费力

建设方案的结论是：去掉人工作业环节，用「双端一体化 + 多数字员工分工」重构舆情流水线，只保留前期的规则配置与后期的结果复核。

1.2 项目目标

以 「全自动采集 + 大模型研判 + 主动触达 + 一键出报」 实现五个可衡量目标：

目标衡量指标达成时限
全程无人化日常运行无需人工启动/监控/整理；人工仅参与规则配置与结果复核本期
采集不遗漏采集任务 7×24 连续运行；重点渠道实时监听，普通渠道按配置周期轮询本期
数据不重复全流程以原文链接为唯一去重主键，同源转发不重复统计，去重率 100%本期
触达要主动达到预警标准的舆情，从研判完成到企业微信触达 ≤ 120s本期
出报要自动日报每日定时自动生成并推送；月报每月自动归集生成本期

1.3 目标用户

角色画像使用端核心诉求
系统管理员平台运维PC渠道/账号/权限/系统配置，全局可控
舆情主管负责人PC + 企业微信配置监测任务与关键词、管推送预警节奏、看整体态势
研判员业务研判岗PC + 企业微信复核大模型研判结论、修正标签与等级、标注训练样本

22. 功能需求

2.1 功能模块列表

模块 1: 监测任务管理

需求ID: REQ-001
功能描述:
监测任务是自动化作业的配置基座，把"抓什么、多久抓一次、怎么判、推给谁、出什么报"五类规则打包为一个可启停的任务单元。支持常态化任务（后台统一配置、长期生效）与临时/专项任务（企业微信端随时发布）。任务变更即时生效，无需重启服务。

用户故事:

  • 作为舆情主管, 我希望一次配置好抓取范围、关键词与推送规则并长期生效, 以便不必每天重复设置
  • 作为舆情主管, 我希望突发舆情时能立刻发布一个专项临时任务, 以便快速摸排事件全貌
  • 作为系统管理员, 我希望停用某个任务后其历史数据仍可查, 以便保留完整台账

验收标准:

  • 验收标准 1: When 用户提交任务表单, the system shall 校验任务名称、任务类型、至少 1 个关键词组、至少 1 个采集渠道为必填, 缺失时前端定位到出错字段并拦截提交
  • 验收标准 2: The system shall 保证任务名称全局唯一, 重复时提示"该任务名称已存在"且不落库
  • 验收标准 3: When 舆情主管在 PC 端创建任务, the system shall 支持选择任务类型为 normal（常态化）/temporary（临时）/special（专项）
  • 验收标准 4: When 用户在企业微信端发布任务, the system shall 自动把任务来源标记为 wecom, PC 端任务列表可查且状态与移动端实时同步
  • 验收标准 5: When 任务被停用（状态置为 paused）, the system shall 立即停止其采集调度, 但已采集数据、研判结论、推送与报告记录全部保留可查
  • 验收标准 6: When 临时/专项任务到达配置的结束时间, the system shall 自动置为 archived 并保留历史数据
  • 验收标准 7: The system shall 记录任务的创建人、创建时间、最后修改人与修改时间, 并在任务详情页展示变更留痕
  • 验收标准 8: If 任务配置引用的关键词组或渠道已被删除, then the system shall 在任务详情页高亮提示失效引用, 并阻止任务被启用
  • 验收标准 9: When 任务的关键词、渠道或频率被修改, the system shall 在下一次调度周期即按新规则执行, 不要求重启服务
  • 验收标准 10: The system shall 对任务的增删改与启停操作写入操作日志, 记录操作人、时间与变更前后状态

优先级: High

模块 2: 关键词库管理

需求ID: REQ-002
功能描述:
关键词库是"抓什么"的语义入口，决定采集与过滤的边界。支持精准关键词（完全匹配）、模糊关键词（包含匹配）、否定关键词（命中即排除）、组合关键词（布尔表达式），并按核心监测词、关联监测词、屏蔽词三类归档。支持单条录入与批量文本/Excel 导入。

用户故事:

  • 作为舆情主管, 我希望用否定词和屏蔽词过滤掉无关内容, 以便大幅减少无效舆情
  • 作为舆情主管, 我希望把监测词按核心/关联/屏蔽分类归档, 以便按任务灵活组合引用

验收标准:

  • 验收标准 1: The system shall 支持 precise（精准）/fuzzy（模糊）/negative（否定）/combo（组合）四种关键词类型并存
  • 验收标准 2: The system shall 按 core（核心监测词）/related（关联监测词）/block（屏蔽词）三类归档关键词, 且同一分类下关键词文本唯一
  • 验收标准 3: When 用户选择关键词类型为 combo, the system shall 要求填写布尔表达式并提供语法校验, 表达式非法时给出具体错误位置
  • 验收标准 4: When 用户批量导入关键词, the system shall 支持粘贴文本（一行一词）与上传 Excel 两种方式, 并逐行返回成功/重复/非法明细
  • 验收标准 5: If 导入的批量数据超过 2000 行, then the system shall 提示分批导入且不执行入库
  • 验收标准 6: When 用户停用某关键词, the system shall 使该词在下一次采集调度中不再生效, 但不删除历史关联数据
  • 验收标准 7: The system shall 在关键词列表展示每个关键词被引用（被任务、预警规则、降噪规则引用）的次数, 支持按引用次数排序
  • 验收标准 8: If 关键词已被任务引用, then the system shall 允许停用但禁止物理删除, 并提示引用该词的任务数量
  • 验收标准 9: The system shall 对关键词的增删改与批量导入写入操作日志

优先级: High

模块 3: 采集渠道管理

需求ID: REQ-003
功能描述:
维护全网采集渠道字典，覆盖社交平台、新闻媒体、论坛贴吧、短视频平台、问答社区、博客专栏、数字报等类别。渠道可绑定采集器、设置渠道级开关与频率覆盖、配置反爬参数（请求间隔、代理池分组、并发上限），供监测任务按渠道勾选。

用户故事:

  • 作为系统管理员, 我希望按渠道单独控制采集开关与频率, 以便高频渠道单独提速、脆弱渠道降低压力
  • 作为系统管理员, 我希望给渠道绑定代理池与限流参数, 以便降低被平台拦截的概率

验收标准:

  • 验收标准 1: The system shall 内置渠道类别字典, 覆盖 social/news/forum/video/qa/blog/epaper 七类, 且支持新增自定义类别
  • 验收标准 2: The system shall 支持渠道名称唯一性校验, 并按类别、状态筛选渠道列表
  • 验收标准 3: When 渠道被停用, the system shall 使其不再被新建任务勾选, 已有任务中的该渠道高亮提示失效
  • 验收标准 4: When 用户为渠道设置频率覆盖值, the system shall 对引用该渠道的所有任务生效, 优先级高于任务级频率
  • 验收标准 5: The system shall 支持配置请求间隔（毫秒）、并发上限、代理池分组、User-Agent 池标识, 并校验取值区间合法
  • 验收标准 6: The system shall 记录渠道最近一次采集时间、近 24 小时采集条数、近 24 小时失败率并展示在渠道列表
  • 验收标准 7: If 某渠道近 24 小时失败率超过配置阈值, then the system shall 在渠道列表标红并在运行监控页生成一条异常提醒
  • 验收标准 8: The system shall 对渠道的增删改与启停写入操作日志

优先级: Medium

模块 4: 全网自动采集与调度

需求ID: REQ-004
功能描述:
系统按任务预设规则启动 7×24 无人值守采集，全程无需人工启动、监控、整理。支持定时轮询、增量抓取、实时监听三种策略并行；采用多模态模型与智能体混合的拟人化操作方式提升覆盖与存活率；配置反爬策略、IP 轮换与请求限流。原始数据完整落库，保留溯源依据。

用户故事:

  • 作为舆情主管, 我希望系统 7×24 自动抓取并自动去重归档, 以便不必人工值守
  • 作为研判员, 我希望采集结果带有完整的互动数据与属地信息, 以便研判传播态势

验收标准:

  • 验收标准 1: The system shall 支持 polling（定时轮询）/incremental（增量抓取）/realtime（实时监听）三种采集策略, 可按渠道分别配置
  • 验收标准 2: The system shall 支持采集频率按秒级、分钟级、小时级、日级四档配置, 并校验最小间隔不低于渠道限流下限
  • 验收标准 3: The system shall 对每条舆情采集以下字段：标题、原文内容、发布链接、发布时间、发布作者、点赞量、评论量、转发量、阅读量、发布地域、设备信息、话题标签
  • 验收标准 4: The system shall 将原始采集数据完整入库, 不做有损截断, 并保留采集批次与采集时间用于溯源
  • 验收标准 5: When 采集请求返回失败, the system shall 按退避策略自动重试, 重试次数可配置, 超过上限则记录失败明细并继续后续任务, 不阻塞整体调度
  • 验收标准 6: The system shall 在采集链路启用 IP 轮换与请求限流, 单渠道并发不超过配置上限
  • 验收标准 7: When 采集到的新舆情链接已存在于库中, the system shall 直接判定重复并剔除, 不重复入库、不重复进入研判
  • 验收标准 8: The system shall 提供采集运行概览：累计采集条数、当日采集条数、去重剔除条数、失败条数、各任务最近执行时间
  • 验收标准 9: If 某任务连续 N 次调度零采集或全部失败, then the system shall 在运行监控页生成告警并向企业微信推送异常提醒
  • 验收标准 10: The system shall 逐条记录采集日志（任务、渠道、批次、结果、耗时、失败原因）, 支持按任务与时间范围筛选

优先级: High

模块 5: 手动链接导入

需求ID: REQ-005
功能描述:
针对系统未覆盖的小众平台、专项舆情链接与人工发现的重点舆情，提供专属链接导入通道。支持单条链接手动输入与 Excel 批量导入两种方式；导入后系统自动发起定向解析，抓取该链接的完整内容、互动数据与发布信息，纳入原始舆情库与自动化采集数据同源管理，后续统一进入净化与研判流程。

用户故事:

  • 作为研判员, 我希望把人工发现的重点链接导入系统, 以便它和自动采集的数据走同一套研判流程
  • 作为研判员, 我希望批量导入后看到失败链接明细, 以便修正后重传

验收标准:

  • 验收标准 1: The system shall 支持单条链接输入导入, 并在提交前校验链接格式合法性

33. 非功能需求

3.1 性能要求

  • 台账列表查询响应时间: < 500ms（95th percentile，基于索引与预聚合）
  • 统计看板加载: < 1s（基于 yq_stats_daily 预聚合结果，不实时计算）
  • 采集吞吐: 单渠道 ≥ 500 条/分钟；全平台累计日均采集 ≥ 5 万条
  • 大模型研判吞吐: ≥ 200 条/分钟（批量并发调用，受模型侧限流影响）
  • 采集入库 → 企业微信触达: ≤ 120s（高风险即时推送链路）
  • 日报生成（含排版与导出）: < 60s
  • 月报生成（含跨月统计与导出）: < 180s
  • 链接批量导入解析: 500 条 < 5min
  • 报告导出 PDF/Word: 单份 < 15s
  • 全文检索: 100 万条量级下 < 1s
  • 数据量基线: 舆情主表年增 ≤ 2000 万条；互动数据快照保留 ≤ 30 天日粒度

必须索引:

  • yq_opinion.url_hash（唯一，去重主键载体）、yq_opinion.publish_time、yq_opinion.channel_id、yq_opinion.task_id、yq_opinion.senti_attr、yq_opinion.risk_level、yq_opinion.clean_status、yq_opinion.analyze_status、yq_opinion.cluster_id
  • yq_alert.status、yq_alert.trigger_time
  • yq_push_record.send_time、yq_push_record.send_status
  • yq_report.report_type、yq_report.report_date
  • yq_collect_log.task_id、yq_collect_log.batch_no
  • yq_knowledge.case_type

3.2 安全要求

  • 登录复用若依账号密码体系；PC 端账号密码 + 图形验证码；企业微信端走网页授权免登并绑定若依用户
  • 所有接口配置 Sa-Token 权限注解 @SaCheckPermission("yuqing:xxx:xxx")，禁止仅靠前端隐藏入口做权限控制
  • 数据权限：复用 @DataScope 思路，扩展为按监测任务/渠道/部门过滤（舆情主管仅见授权范围）
  • 所有 @RequestBody 参数加 @Validated；所有自由文本字段（关键词、备注、处置说明、案例描述、任务名称）加 @Xss 防存储型 XSS
  • 采集内容原样入库，渲染到前端时必须转义，禁止 v-html 直接渲染采集正文
  • 所有 CUD、规则变更、报告提交、权限变更、数据导出、链接导入加 @Log 操作日志
  • 企业微信推送鉴权凭据（CorpId / Secret / AgentId）加密存储于配置中心，禁止硬编码进代码或提交仓库
  • 大模型 API Key 加密存储并支持轮换；调用日志脱敏，不外带未授权数据
  • 采集反爬配置（代理池账号、Cookie）加密存储；采集器与业务服务网络隔离
  • 报告与附件文件仅存 MinIO，数据库仅存 URL 与元信息；文件访问需鉴权或使用带有效期的签名 URL
  • 上传文件类型与大小校验（导入 Excel 仅 .xlsx/.xls，≤10MB）
  • 报告对外提报前支持敏感字段审核标记，防止内部研判口径外泄

3.3 兼容性要求

  • PC 浏览器: Chrome 90+ / Edge 90+（管理后台不要求 Safari）
  • PC 分辨率: 最低 1366×768，主内容区适配 1440 / 1920
  • 移动端 H5: 企业微信内置浏览器（iOS / Android）为主；兼容微信内置浏览器与手机 Chrome/Safari 最新两个大版本
  • H5 适配: 基于 RuoYi-App-Plus（uniapp），一套代码产出 H5；需适配 iOS 安全区与安卓刘海屏
  • 后端: JDK 21，Spring Boot 3.x，MyBatis-Plus 3.5.x，Sa-Token 1.3x
  • 数据库: MySQL 8.0+（utf8mb4，事务 / 配置 / 状态库）+ Apache Doris 2.1/3.0（舆情事实与分析库）双库分离，落库归属见 §5 引言与 §5.5；缓存 Redis 6+
  • 前端 PC: Vue 3.4+ / TypeScript 5.x / Element Plus 2.x / Vite 5.x
  • 中间件: 定时任务复用若依 snapshot 定时任务；对象存储 MinIO（S3 兼容自建）

55. 数据模型

存储归属（MySQL + Doris 双库）: 舆情数据体量大、只增不改、聚合查询密集，故与事务/配置数据分离存储（详见《技术架构说明》§4）。

存储承接内容表清单
MySQL 8.0（事务 / 配置 / 状态）若依基座、配置型数据、状态机、知识库与模型元数据sys_*、yq_task、yq_task_channel、yq_task_keyword、yq_keyword、yq_keyword_group、yq_channel、yq_noise_rule、yq_level_rule、yq_alert_rule、yq_push_rule、yq_push_template、yq_report_template、yq_report_section、yq_alert、yq_push_record、yq_report、yq_report_opinion、yq_knowledge、yq_model_version、yq_train_sample、yq_tag、yq_wecom_command
Apache Doris（事实与分析）只增不改、体量亿级、多维聚合的舆情事实与预聚合数据yq_opinion、yq_opinion_analysis、yq_opinion_metric、yq_opinion_tag、yq_opinion_cluster、yq_collect_log、yq_stats_daily（共 7 张）

归属判据: 有事务 / 状态机 / 频繁更新 / 体量小 → MySQL；只增不改 / 体量大 / 聚合多 → Doris。
一致性边界: 两库以 opinion_id、url_hash 关联，不做跨库事务，采用最终一致 + 状态补偿。
写入边界: MySQL 由业务 API 写入；Doris 仅由采集与研判 Worker 经 Stream Load 批量写入（攒批 5s / 1000 条，label 幂等 + url_hash Unique Key 去重）；业务查询侧对 Doris 只读。
建表规范与示例 DDL 见 §5.5；数据源路由 见 §6.3；账号与权限 见 §7.4。

报告模板 (yq_report_template) 1 ──── N 报告模板章节 (yq_report_section)
报告模板 (yq_report_template) 1 ──── N 报告 (yq_report)
报告 (yq_report) 1 ──── N 报告舆情关联 (yq_report_opinion) ──引用──▶ 舆情 (yq_opinion)
知识库案例 (yq_knowledge) 1 ──── N 训练样本 (yq_train_sample)
模型版本 (yq_model_version) 1 ──── N 训练样本 (yq_train_sample)
企业微信指令 (yq_wecom_command) ──关联──▶ 监测任务 / 报告
统计预聚合 (yq_stats_daily) ──汇总自──▶ 舆情 (yq_opinion)

核心约束:

  • yq_opinion.url_hash 全局唯一，是全流程唯一去重主键（opinion_url 原文可超长，用其 SHA-256 承载唯一索引）
  • 一条舆情归属唯一监测任务（链接导入可为空或指向虚拟任务）与唯一采集渠道
  • 一条舆情最多一条有效研判结果；重研判覆盖旧结果并递增 analyze_version
  • 只有达到预警标准的舆情才生成预警记录
  • 只有 generated 状态的报告才能被提交
  • 同一报告类型的默认模板唯一
  • 知识库案例必须关联来源舆情或人工录入标记

5.5 Doris 建表约定与写入链路

落 Doris 的 7 张表（见 §5 引言）按以下通则建模；MySQL 侧表结构与 §5.2 数据字典完全一致，Doris 侧类型按本节映射。

表设计通则:

项约定
表模型明细事实用 Unique Key(url_hash) + Merge-on-Write，天然承接全流程链接去重（重复写入自动 upsert 覆盖）；纯追加的日志/预聚合类可用 Duplicate Key 或 Aggregate Key
分区yq_opinion 按 collect_date 动态分区，dynamic_partition.start = -1095（保留 3 年自动滚动）；yq_opinion_metric / yq_collect_log 按天分区，保留 30 ~ 180 天
分桶DISTRIBUTED BY HASH(url_hash) BUCKETS 16（按 BE 数量与数据量调整，单桶 1~10 GB 为宜）
副本replication_num = 3（生产自建集群）；开发环境可设 1
索引title、content 建中文分词倒排索引（"parser" = "chinese"，需 Doris 2.0.2+），支撑「全文检索 100 万条 <1s」；task_id / channel_id / senti_attr / risk_level 建 BloomFilter 或前缀索引
类型映射Doris 无 JSON 明细列时用 VARCHAR/STRING 存 JSON 文本；时间用 DATETIME；分区列须为 DATE/DATETIME 且置于 schema 首位
分区列 vs 主键Unique Key 必须包含分区列，即 UNIQUE KEY(collect_date, url_hash)；跨天重复链接由 url_hash 业务唯一性 + 应用侧判重兜底

写入链路（Stream Load，无消息中间件）:

  • 接口: PUT /api/{db}/{table}/_stream_load，Header 带 label（幂等键，同 label 重复导入自动去重）、format: json、strip_outer_array: true
  • 攒批: 采集 / 研判 Worker 侧按 5s 或 1000 条触发一次批量写入；攒批靠有界阻塞队列 + 本地磁盘暂存（无需 Kafka）

6.4 错误响应格式约定

RuoYi-Vue-Plus v6 统一响应体:

{
  "code": 500,
  "msg": "该任务名称已存在",
  "data": null
