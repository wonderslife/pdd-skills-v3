四、免登数据流（8 步）

免登是 F-012 里技术含量最高的部分。写法上刻意对齐若依自带的 PasswordAuthStrategy：只有让免登签发的 token 与账号密码登录签发的 token 结构完全一致，H5 端 App-Token 的后续请求才能通过 @SaCheckPermission 鉴权。

企微工作台 → H5 auth.vue（onLoad 拿到 code） → GET /yuqing/wecom/auth?code=xxx&clientId=428a8310… → WecomTokenHolder.get() ← 复用 F-011，返回 access_token → GET /cgi-bin/auth/getuserinfo ← 企微 API，换 UserId（失败自动刷新 token 重试一次） → WecomBindResolver.resolve() ← 三级映射（见下） → 校验用户状态（停用 / 已删除一律拒绝） → loginService.buildLoginUser(user) → loginUser.setClientKey() / setDeviceType() ← 关键：app 端 client 上下文 → IAuthStrategy.buildLoginParameter(client) → LoginHelper.login(loginUser, model) → bindResolver.recordBinding() ← 留痕，失败不阻塞 → 返回 WecomAuthVo{ accessToken, expireIn, userId, wecomUserId, success } → H5 setToken() 写入 App-Token → 进入 work.vue

绑定映射三级（安全关键）

  1. 命中历史绑定：查 yq_wecom_command 中该成员最近一次登记的 user_id
  2. 按登录名匹配：sys_user.user_name == wecomUserId（仅在 auto-bind-by-login-name=true 时启用）
  3. 都匹配不到：返回 null → 明确拒绝并提示，绝不静默创建账号
越权风险提示：第 2 级「按登录名自动绑定」存在「同名不同人」被误绑成同一账号的风险。若企业环境的企微成员 ID 与域账号不一致（很常见），必须把 auto-bind-by-login-name 置为 false，改由管理员在 PC 端手工维护绑定关系。

五、指令解析引擎设计

规则解析，不做大模型调用。理由：确定性 + 零成本 + 可审计，且不会因为大模型不可用而让整条链路挂掉。

解析与执行分离

  • WecomCommandParser —— 纯函数，不碰 Spring / DB / 网络，输入字符串输出 ParsedCommand。这是 F-012 里唯一可离线断言的部分。
  • YqWecomExtServiceImpl.execute() —— 真正的执行，且先过权限判定。越权返回 denied 并给出可读提示（验标 10：不依赖前端隐藏按钮）。

这个分离是为了避免「一句话就把任务建了」的越权风险 —— 解析无害，执行才需要授权。

六、复用 F-011 基建的一处关键决策

WecomTokenHolder 在本项目里不是 Spring Bean —— 它由 YqAlertConfig 手工 new 出来。这是必须处理的问题。

为什么不能各 new 一个：企业微信同一自建应用的 access_token 是全局唯一的，新换的会顶掉旧的。如果免登和推送各持有一个 token 持有者，两者会交替刷新、互相顶号，导致推送与免登间歇性 42001 失败。

解决：新增 YqWecomConfig，把 WecomTokenHolder 装配成单例 Bean，免登与推送共用同一实例。配置类注释里写清了这条约束，避免后人重构时踩回去。

七、本轮自测抓出的 5 个真实缺陷

离线自测先跑出 3 个失败（184 PASS / 3 FAIL），修复后又暴露 1 个，加补用例后收敛到全绿。这 5 个缺陷都不是「猜出来的」，是断言跑出来的。

#缺陷现象修法
1 三层转义错位（编译期） 模板里写 \\" 产出的是字面 " 而非 Java 的 \"，生成 sb.append("": "") → 编译失败 ')' or ',' expected 正确写法是模板里写 \\"（\\→\、"→"）。Java 里所有带转义的字符串都要按这个层级算
2 未识别时参数丢失 parse() 里「未识别则 return」放在参数抽取之前 → 未命中关键词的指令连 untilText 都一起丢，排查时看不到任何有用信息 参数抽取统一提前，UNKNOWN 也返回抽到的参数 + reason；已加防回归用例
3 平票仲裁顺序错 「研判一下这条舆情」→ 误判 QUERY_OPINION（应为 TRIGGER_ANALYSIS） 声明顺序改为「具体意图优先」；注释写明顺序即仲裁规则
4 ABOUT/QUERY_OF 贪婪吞句 「关于台风的临时任务」→ 抽出整段「台风的临时任务」而非「台风」 终止符加 的等和与
5 UNTIL 贪婪 「到今晚8点结束」→ 抽出「今晚8点结束」 终止符加 结束为止之前

另外补了一个「口语化」用例：建个任务（带「个」）比 建任务 更贴近真实输入，已纳入关键词表。

九、已知边界（不藏着）

  1. 免登链路未经真实企微联调。离线自测只覆盖了指令解析（纯函数）。免登依赖企业微信真实网络接口与凭据，无法离线覆盖 —— 此处不假装覆盖。
  2. 企微凭据尚未配置。yq_wecom.yml 里 corpId / corpSecret / agentId 均为环境变量占位。未配置时免登接口返回可读失败原因，H5 自动降级到账号密码登录，不阻塞使用。
  3. 免登与推送是否同一自建应用未定。若是同一应用填相同凭据即可；若不同，需把 YqWecomConfig 里的 token 持有者切换为按 YqWecomProperties 构造的独立实例（企微不同应用的 token 相互独立，此时互不干扰）。
  4. 报告触发是「如实返回不可用」。F-014/015 生成引擎未落地，triggerReport 返回 status=unavailable 并说明原因，不假装成功。
  5. 研判 / 建任务的执行是「受理 + 回推」。真实建任务需 F-001 的任务服务联动，当前只落指令日志与受理回执；研判需 F-007。
  6. H5 前端存在 3 处存量类型错误（alert/index.vue 的 maxlength 传字符串、mine.vue / work.vue 的 icon 类型），最后修改时间为 9/21–9/22，早于本次工作，非本次引入。修复需改主生成器 gen-yuqing.mjs，属独立议题。
  7. 指令解析未接入大模型兜底。规则未命中时不做大模型调用。若后续要加，应仅作为「建议」并需人工确认，避免误触发写操作。
