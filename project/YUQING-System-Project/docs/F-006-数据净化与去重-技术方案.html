F-006 数据净化与链接去重 · 技术方案

来源 dev-spec F-006-dedup.md（优先级 P0，REQ-006） · 编制 2026-09-22 · 状态：设计完成，待确认后实现
一句话：把采集管线里那句占位注释「真正的降噪规则匹配属 F-006，此处只兜底空壳记录」换成真引擎， 并让「剔除」这件事可追溯、可统计、可重跑——而不是丢掉就算了。

1. 现状：已经有什么，缺什么

采集管线 CollectPipeline.dedupeAndFilter() 现有 6 步，其中第 3 步是明确的预留位：

① 链接归一化 → sha256 写入 url_hash
② 关键词组合条件过滤（P0-1 已实现）
③ 无效内容剔除 ← 现在只有 blockDetector.looksLikeTrap(...) 兜底，
                   源码注释原文写着「真正的降噪规则匹配属 F-006」
④ 批次内去重（batchSeen）
⑤ 全局去重（UrlHashDeduplicator.firstSeen）
⑥ 快照留存（SnapshotStore）→ 入库
能力现状说明
链接归一化 + SHA-256已有UrlNormalizer.normalize() / sha256()
批次内外两级去重已有UrlHashDeduplicator + batchSeen
降噪规则表 + CRUD已有yq_noise_rule 建表 + YqNoiseRuleController 全套 CRUD
清洗状态字典已有yq_clean_status = raw / cleaned / rejected
降噪类别字典（7 类）已有yq_noise_category，值与验收标准 1 完全对齐（见 §3）
降噪规则引擎缺失没有任何类读取 yq_noise_rule 做判定
剔除原因落库缺失被剔除的记录直接 continue 丢掉，noise_reason 永远是 NULL
跨渠道重复标记缺失yq_opinion 只有单个 channel_id，无处记录「其他渠道也采到了」
批量重跑 + 预览缺失验收标准 9
去重率 / 剔除率看板缺失验收标准 7
关键判断：yq_noise_rule 这张表现在是「有表、有 CRUD、但没人用」的死表。 F-006 的实质是给它接上消费者，而不是重新发明一套规则模型。

2. 架构与分层

                     ┌──────────────────────────────────────┐
   采集链路           │ CollectPipeline.dedupeAndFilter()     │
                     └───────────────┬──────────────────────┘
                                     │ ③ 位
                     ┌───────────────▼──────────────────────┐
   编排层             │ NoiseRuleEngine.judge(raw)            │
                     │   → CleanVerdict {status, category,   │
                     │                   reason, ruleId}     │
                     └───────────────┬──────────────────────┘
                                     │ 按 priority 升序依次试
        ┌────────────────────────────┼────────────────────────────┐
        ▼            ▼               ▼              ▼             ▼
   BlankDetector  BotDetector  MeaninglessDet  AdvertDet   FloodingDet ...
   （固定判定）   （固定判定） （长度/信息量）  （规则驱动） （规则驱动）
                                     │
                     ┌───────────────▼──────────────────────┐
   规则装载层         │ NoiseRuleLoader                       │
                     │  读 yq_noise_rule(status=0) → 编译    │
                     │  → 按 priority 升序 → 进程内缓存      │
                     │  → 规则变更 / 手动刷新时失效          │
                     └──────────────────────────────────────┘

为什么分「固定判定」和「规则驱动」两类

  • 空白内容、机器人内容：判定逻辑是确定的（空文本 / UA 特征 / 发布频率异常）， 不需要业务配规则，硬编码为策略类即可，配了反而容易配错。
  • 广告营销、灌水、无意义短句、违规屏蔽：关键词和正则必须让业务随时改， 走 yq_noise_rule 表驱动，match_type ∈ keyword / regex。

7 类全部保留在 noise_category 维度上，业务可在降噪规则页按类别筛选、统计—— 即使某一类是硬编码判定，也照样产出 category，统计口径统一。

3. 七类降噪类别（与字典实测一致）

dict_value中文判定方式判定要点
spam垃圾内容规则驱动关键词 / 正则命中即剔除
advertisement广告营销规则驱动加微信、扫码、优惠领取等营销话术
flooding灌水评论规则驱动 + 频次同批次内同一正文重复 ≥ N 次，超出部分剔除
meaningless无意义短句规则驱动 + 长度去空白字符后长度 < 阈值，或纯符号 / 纯重复字符
bot机器人内容固定判定作者名为空且无互动量，或 UA/设备信息异常
blank空白内容固定判定标题与正文同时为空 / 仅空白字符
violation违规屏蔽规则驱动命中违禁词库，剔除且不进入研判
与验收标准的对齐核验：验收标准 1 要求「垃圾内容、广告营销、重复灌水评论、无意义短句、 机器人发布内容、空白内容、违规屏蔽内容」七类——字典 yq_noise_category 实测值为 spam/advertisement/flooding/meaningless/bot/blank/violation， 一一对应，无需新增字典项。

4. 数据流：一条舆情从采集到入库

fetch()
  │
  ▼ ① UrlNormalizer.normalize() → sha256 → raw.urlHash
  ▼ ② KeywordMatcher.accept()  ← P0-1，未命中记 filteredCount
  ▼ ③ NoiseRuleEngine.judge(raw)          ← ★ F-006 新增
  │      ├─ rejected → raw.cleanStatus='rejected'
  │      │             raw.noiseReason = "[类别] 命中规则《名称》"
  │      │             result.rejectedCount++
  │      │             → 仍写入 yq_opinion（状态 rejected），不进研判
  │      └─ pass     → raw.cleanStatus='cleaned'
  ▼ ④ batchSeen 批次内去重
  ▼ ⑤ UrlHashDeduplicator.firstSeen() 全局去重
  │      └─ 已存在 → 见下方「跨渠道」处理
  ▼ ⑥ SnapshotStore.store() → CollectJdbcWriter 入库

验收标准 8：跨渠道重复怎么落地

要求「同一链接被不同渠道重复采集 → 只保留首条有效记录，并在其来源渠道字段补充其他渠道标识」。

现有 yq_opinion.channel_id 是单值，装不下。方案是加一列而不是改主键：

ALTER TABLE yq_opinion ADD COLUMN dup_channel_ids VARCHAR(200)
    DEFAULT NULL COMMENT '重复采集到的其他渠道ID（逗号分隔）';

命中全局去重时：

  1. 按 url_hash 反查已入库那条记录的 opinion_id；
  2. 把当前 channel_id 追加进它的 dup_channel_ids（去重、定长截断保护）；
  3. 当前这条不入库，计 dupCount。
需要你拍板：Doris 的 Unique Key 是 (collect_date, url_hash)， 即按天分区。这意味着「同一链接今天采到、明天又采到」在库里是两行。
  • 方案 A（按天去重，推荐）：跨天不算重复。契合 Doris 分区语义， 且舆情本身需要「同一事件多天传播」的观测能力。跨渠道合并只在同日内生效。
  • 方案 B（全局去重）：跨天也算重复，需额外维护一张 url_hash → opinion_id 的全局索引表 （MySQL 侧），写入前多一次查表，且 Doris 侧要容忍「更新历史分区」。
我倾向 A：省一张表、少一次 IO，且不破坏分区裁剪。

「去重率 / 降噪剔除率」的口径（必须先定死，否则前后端各算各的）

去重率     = dupCount / (fetchedCount)                ← 分母是「召回量」，不是入库量
降噪剔除率 = rejectedCount / (fetchedCount - dupCount) ← 分母已排除重复，避免重复条目稀释剔除率

两者分母不同是刻意的：去重发生在降噪之后（见 §4 顺序）， 若剔除率用 fetchedCount 做分母，重复条目会把剔除率压低，看板上会「看起来很干净」。

9. 待确认（2 项，影响表结构与实现量）

Q1 跨天去重：同一链接今天采到、明天又采到，算重复吗？
→ 方案 A「按天去重」（推荐，不加表）/ 方案 B「全局去重」（加一张 url_hash 索引表）。
Q2 重跑记录载体：验收标准 9 要求「执行结果记录」。
→ 方案 A 新建 yq_clean_batch 表（语义清晰，多一张表 + CRUD）
→ 方案 B 复用 yq_collect_log 加 batch_type 字段（不加表，但语义混杂）

10. 安全基线（实现时必须满足）

  • 越权：新增接口一律 @SaCheckPermission；任务/渠道归属校验只信 LoginHelper，不信请求体。
  • 注入：规则查询全用 LambdaQueryWrapper，禁用 ${} 拼接。
  • ReDoS：业务可配正则是本模块最大的攻击面。规则编译必须设超时与长度上限， 对超长/嵌套量词正则直接拒绝并提示，避免一条规则拖垮整个采集线程池。
  • XSS：剔除原因与规则名会回显到台账页，渲染前按既有白名单净化。
