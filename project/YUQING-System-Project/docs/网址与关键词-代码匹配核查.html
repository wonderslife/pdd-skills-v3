4.2 语法与 PRD 冲突

来源写法
你的关键词样例(辽宁|沈阳|大连|...)+(药监局|药品|医疗器械|...)
PRD §5.2 字段字典（第 932 行）"(A or B) not C"
必须二选一。建议以你的实际样例为准反向修订 PRD——因为这是从业务侧来的真实词表，| 加 + 的写法更贴近舆情行业的通行表达，也便于批量导入。改 PRD 的成本远低于改业务同事的录入习惯。

4.3 代码事实：三处断点

逐行核对后确认，组合表达式在采集链路上一次都没有被真正使用过：

// YqCollectServiceImpl.loadKeywords()  —— 只 select keyword_text
return keywordMapper.selectByIds(ids).stream()
    .filter(keyword -> STATUS_ENABLED.equals(keyword.getStatus()))
    .map(YqKeyword::getKeywordText)   // ← keyword_type / keyword_category
    .filter(StringUtils::isNotBlank)  //   / combo_expression 全部丢弃
    .distinct().collect(Collectors.toList());

// AbstractSiteAdapter.firstKeyword()  —— 只取第一个
for (String kw : keywords) {
    if (StringUtils.isNotBlank(kw)) return kw.trim();   // ← 立即 return
}

// AbstractSiteAdapter.fillUrl()  —— 整串编码
String url = template.replace(props.getKeywordPlaceholder(), urlEncode(keyword));

全仓检索 comboExpression 只有两处命中：YqKeyword.java:51 的域字段声明，和 YqKeywordServiceImpl.java:96 的一个 like 查询条件。没有解析器、没有校验器、没有执行器。

而 F-002 验收标准 3 明确要求：「When 用户选择关键词类型为 combo, the system shall 要求填写布尔表达式并提供语法校验, 表达式非法时给出具体错误位置」——该条未达标。

4.4 后果推演

按现有代码，样例 1 会这样执行：

  1. loadKeywords 拿到 2 条 keyword_text（如果是两条独立关键词的话）；
  2. firstKeyword 取第一条；
  3. urlEncode 把 (辽宁|沈阳|...)+(药监局|...) 整串编码；
  4. 拼进 https://www.baidu.com/s?...&wd=%28%E8%BE%BD%E5%AE%81%7C...。

百度不认 + 连接两组、| 表示或的语法，会把整串当作字面查询词 → 返回 0 条结果且不报错。政务站内搜索同理。这就是最危险的情况：引擎显示「采集成功、入库 0 条」，看起来像正常空窗，实际是配置根本没生效。

4.5 组合语义的三种落地方式

方式做法请求量命中率适用
A 笛卡尔展开16 地区 × 6 主题 → 96 个独立检索词逐个搜×96最高站点搜索只支持单词
B 高级语法透传只对百度/Bing 等支持布尔语法的引擎透传表达式×1中搜索引擎类渠道
C 单侧检索 + 本地判定用主题词（药监局）检索，拿到结果后本地跑组合正则筛地区×6高推荐，成本与覆盖平衡最好
推荐 C。既能控住请求量（受渠道 request_interval 与 concurrency_limit 约束，A 方案的 96 倍放大在抖音这类渠道上会被限流打回），又能保证召回。实现上需要在适配器里加一层「本地命中判定」，把 combo_expression 编译成 Pattern 做二次过滤。

5.2 任务级降噪的结构缺口

从词表内容能明确看出，排除词是按任务分组的：

词组样本归属任务
「东北超」误匹配词东北超哥 / 东北超火 / 外穿东北超 / 东北超自然 / 东北超保暖 …（约 100+ 条）样例 2（东北足球超级联赛）
通用噪声词国事访问 / 被查 / 离职 / 妈妈 / 爆款 / 套餐 / 湖南 / 四川 / 美国 …跨任务通用

但 yq_noise_rule 是全局表，没有 task_id。如果把这些词全部灌进全局降噪规则，样例 1（药监局监测）里出现「被查」「离职」的合法舆情会被一并误杀——**「某药企被查」正是典型的高价值舆情**。

必须补 task_id。两种做法：① yq_noise_rule 加 task_id 字段（NULL 表示全局），降噪时按「任务级优先、全局兜底」匹配；② 排除词挂 yq_task_keyword，靠 keyword_type=negative 天然带上任务维度。方案 ② 更贴合现有结构，也复用了 F-002 已有的分类能力。

5.3 词表质量问题

去重后 177 条，10 个重复词需要清洗：东北超哥 / 外穿东北超 / 东北超火 / 东北超姐 / 东北超人 / 东北超冷 / 超级恶劣 / 超级水区 / 淮安市城市足球联赛 / 超级特产。yq_keyword 有 uk_yq_kwgroup_name 类的唯一约束倾向（同一分类下文本唯一，见 F-002 验收标准 2），导入时需先去重，否则会触发唯一键冲突。

6 表结构层面发现

6.1 悬空外键字段

yq_channel 里有三个字段指向不存在的表：

字段注释表是否存在
collector_id绑定采集器ID无 yq_collector
ua_pool_idUA 池ID无 yq_ua_pool

当前实现里这两个字段从未被读写（UA 由 HeaderPool 内置 10 个真实 UA 轮换，代理由 proxy_group_id 驱动）。建议：要么补上这两张表，要么从表结构和前端表单里移除，避免用户填了没反应。

6.2 配置时的间隔约束（容易踩）

引擎有一条硬校验：任务采集间隔 ≥ max(min-interval-seconds, 渠道请求间隔 × 并发上限)。

当前默认值：request_interval=3000ms、concurrency_limit=2、min-interval-seconds=30 → 3000×2 = 6 秒 < 30 秒 ✓ 通过。

但如果给百度这类站点配 request_interval=500ms、concurrency_limit=4，会得到 2 秒的下限，而 min-interval-seconds 还是 30 → 单元直接被打上 skipReason，日志显示「采集间隔不得低于该渠道限流下限」，任务静默不执行。配置真实站点时必须同步下调 min-interval-seconds。
