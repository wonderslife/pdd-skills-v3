四、引擎设计

4.1 正文净化四步（ContentPurifier）

① 整块抹掉 script / style / iframe / object / embed / noscript（连内容一起丢，防脚本文本被当正文） → ② 剥全部 HTML 标签 → ③ 解码常用实体（&nbsp; &amp; &lt; &gt; &quot; &#39;） → ④ 归一（空白/全角转半角/零宽与控制字符清理/连续空行压缩到 ≤2）。
  • 全程字符扫描，不用正则。抓回来的 HTML 脏得没边（缺闭合、嵌套错乱），正则既慢又容易在畸形输入上回溯爆栈。
  • 安全基线：只产出纯文本，不做「白名单标签放行」。舆情正文属不可信内容，一律降级为文本后再入库与展示，从源头消掉 XSS。
  • 有效字符数按码点统计，避免把 emoji（代理对）算成 2 个字符而误判长文本为短句。

4.2 七类降噪判定顺序（NoiseEngine）

序判定来源说明
1空白内容 blank内置最快，先挡掉空壳记录；空文本跑规则没有意义
2库表规则业务自定义 按 priority 升序，先命中先判定。放在内置判定之前，让「业务说这条该留/该杀」优先于通用启发式
3机器人内容 bot内置作者名 / 设备信息命中爬虫特征（大小写不敏感）
4灌水评论 flooding内置连续重复字符 ≥20，或首 12 字片段重复 ≥3 次
5无意义短句 meaningless内置有效字符数 < 15（可配）

spam / advertisement / violation 三类没有通用启发式，靠库表规则覆盖； yq_noise_rule 此前是死表（有表、有 CRUD、无消费者），本次才真正接上引擎。

4.3 正则写错的处理：降级而非中断

业务在后台填的正则经常写错。编译失败时 不抛异常、不停链路，降级为「按字面量包含匹配」并在 compileError 里留下证据，剔除原因会带上「（正则已降级）」标记，便于后台定位是哪条规则写坏了。 一条坏规则不该让整批采集静默失败 —— 这与 P0 阶段修掉的「采不到东西且不报错」是同一类防线。

4.4 去重与跨渠道合并（CrossChannelMerger）

  • 按天分组：(collect_date, url_hash)；首条 = 采集时间最早的那条（时间相同按列表顺序），保证「首条」语义稳定可复现。
  • 渠道合并：其余条目的 channel_id 并入首条的 dup_channel_ids（去重、排除自身），统计口径仍只算 1 条。
  • 管线内的顺序：关键词过滤 → 净化降噪 → 按天跨渠道合并 → 跨批次 Redis 去重 → 快照落盘。 刻意先净化后去重：反过来会让「首次进来被判垃圾、以后就再也不进来」的错误永久化。

5.1 重跑范围的三道硬校验

  • 采集日范围必须闭合，且跨度 ≤ 366 天；
  • 任务ID与渠道ID至少要给一个 —— 「不限任务 + 不限渠道 + 不限日期」等价于全表重扫，一律拒绝；
  • full_replay 不允许再指定任务/渠道（语义冲突）。

八、已知边界（不粉饰）

  1. 跨渠道合并只覆盖「同一次调度内」。 同一天、跨批次（间隔数小时）撞车的跨渠道重复，会被 Redis 去重拦下并计入 dupChannelCount， 但不会回写首条的渠道列表 —— 攒批写入已落盘，回头改首条要再读一次全量内容，性价比极低。 若后续要补全，正确做法是加一张 (collect_date, url_hash, channel_id) 的旁路表，由净化批次统一回补。
  2. dedupScope=global 未实现：配置成 global 会按 day 处理并打告警日志，不会静默走错逻辑。
  3. 净化会改写历史行的 title/content。重跑执行后，正文是净化后的版本；原文快照仍留在 MinIO（snapshot_key），可回溯。
  4. 不加 @Transactional。yq_opinion 在 Doris、yq_clean_batch 在 MySQL，两者无法共享本地事务； 改用「逐条更新 + 失败即停 + 批次记录标记 failed」，重跑一次即可继续，不会出现半截脏数据被当成成功。
  5. yq_doris_mysql_fallback.sql 仍是手写模板（在 gen-yuqing-collect.mjs 里）。 本次给它补了两列，但长期看应改为生成器产出 —— 中途尝试过由 gen-yuqing.mjs 产出，发现两个生成器会互相覆盖，已回退并保留单一归属。
