# 舆情监测研判报送平台 — 技术架构说明

**版本**: v0.4（新增 §5 数据采集技术专章；已移除 Kafka；7 项已确认决策见 §11.1）
**日期**: 2026-09-18
**关联文档**: 《my-feature.prd》v1.0.0（YUQING-System-Project）
**适用范围**: 本文档补充 PRD §3 / §6 的技术落地细节，重点说明 **Java 后台 + Vue 前端 + MySQL/Doris 双库** 的完整技术架构选型。

> 说明：本平台已定 **Java 后端 + Vue 前端**；舆情数据量大，**事实数据单独建表落 Apache Doris**，与 MySQL 事务库分离。以下逐层给出其余技术栈选型、Doris 建表与同步方案、部署规格与待确认项。

## 1. 架构目标与设计原则

### 1.1 目标

| 目标 | 落地要求 |
|------|---------|
| 海量数据可分析 | 年增舆情 ≤ 2000 万条，保留 3 年；多维聚合（渠道×情感×风险×时间×地域×任务）秒级返回 |
| 全流程自动化 | 采集→净化→研判→预警→推送→出报，人工仅参与规则配置与结果复核 |
| 双端一体 | PC 管理端（Vue3）+ 企业微信内嵌 H5（uniapp），共用若依账号体系 |
| 复用不重造 | 用户/角色/菜单/部门/字典/操作日志/定时任务直接复用若依基座 |
| 可水平扩展 | 采集与研判是高并发异步任务，按 Worker 水平扩展，不拖垮业务 API |

### 1.2 五条设计原则

1. **事务与分析分离（HTAP 不硬扛）**——MySQL 只承接事务型/配置型/状态机型数据，海量事实与聚合下沉 Doris，禁止在 MySQL 里对千万级表做多维聚合。
2. **写路径异步化**——采集与研判在 Worker 内异步解耦，批量攒批后 Stream Load 入仓，不阻塞在线请求。
3. **读路径预聚合**——看板/报表读 Doris 物化视图或 DWS/ADS 预聚合表，不实时扫明细（对齐 PRD「看板 <1s」）。
4. **能复用不新建**——权限、字典、日志、定时、代码生成全部走若依内置能力。
5. **模块化单体起步，任务节点独立扩**——不过早拆微服务；采集/研判/推送/报告以独立可部署进程运行，共享一套领域代码。

## 2. 总体架构

### 2.1 分层视图

```text
接入层   Nginx（反代 / TLS 终结 / 静态资源）
           │
应用层   PC 管理端（Vue3 + TS + Element Plus）   │   企业微信 H5（uniapp）
           │
服务层   RuoYi-Vue-Plus v6.0.0
         ruoyi-admin 业务 API │ 采集 Worker │ 研判 Worker │ 推送服务 │ 报告服务
         SnailJob 调度 │ Sa-Token 认证 │ 若依内置：用户/角色/菜单/字典/日志
           │
数据层   MySQL 8.0             —— 事务 / 配置 / 状态机
         Apache Doris 2.1/3.0  —— 海量舆情事实 · OLAP · 倒排索引
         Redis 6+              —— 缓存 / 分布式锁 / 限流
         MinIO                 —— 采集快照 / 报告文件
           ▲
           └── 采集侧 Stream Load 批量直写（无消息队列）
```

### 2.2 端到端数据流

```text
[采集] 多策略调度 → 抓取原文/元数据 → 本地有界队列 + 磁盘暂存
   │
   ├─► 批量攒批 → Doris Stream Load（HTTP 直写）→ Doris ODS（原始层）
   │
[净化] 降噪规则 + url_hash 去重
   │
   └─► Doris DWD（明细层，Unique Key on url_hash，天然 upsert 去重）◄─┐
   │                                                                  │
[研判] 研判 Worker 调大模型 → 结构化结论 ──► MySQL(状态) + Doris(yq_opinion_analysis)─┘
   │
[聚合] 定时/物化视图 → Doris DWS（预聚合）→ ADS（看板/报表专用）
   │
[预警] 规则评估命中 → MySQL(yq_alert 状态机) → 推送服务 → 企业微信应用消息
   │
[出报] 报告服务渲染 → MinIO(文件) + MySQL(yq_report 元信息/状态)
```

## 4. 数据库架构（重点：MySQL + Doris 双库）

### 4.1 为什么舆情数据要单独走 Doris

**数据量论证**（对齐 PRD §3.1「年增 ≤2000 万条、快照保留 ≤30 天」）：

| 数据 | 量级估算 |
|---|---|
| `yq_opinion` 舆情主表 | 年增 ~2000 万，保留 3 年 → **~6000 万行** |
| `yq_opinion_analysis` 研判结果 | 与主表 1:1，宽表 → ~6000 万行 |
| `yq_opinion_metric` 互动快照 | 日粒度保留 30 天，按活跃舆情展开 → 千万级滚动 |
| `yq_collect_log` 采集日志 | 按批次×渠道，量级 ≥ 主表，保留期长 |
| 标签关联 / 聚类 / 统计 | 百万~千万级 |
| **合计** | **亿级行、TB 级存储** |

**查询特征**：多维交叉聚合（渠道×情感×风险×地域×时间×任务）、TOP 榜、趋势曲线、关键词全文检索——这类 OLAP 负载在 MySQL 千万级之后明显劣化（无列存、无向量化、无 MPP）。

**因此**：舆情事实数据独立建库建表落 **Apache Doris**，MySQL 不再承载。

### 4.2 Doris 的选型优势

| 能力 | 对本案的价值 |
|---|---|
| MPP + 列存 + 向量化执行 | 亿级聚合秒级返回，看板/报表不卡 |
| MySQL 协议兼容 | JDBC 直连，复用 MyBatis/dynamic-datasource，学习成本低 |
| Unique Key 模型（MoW） | 以 `url_hash` 为主键 upsert，**天然承接全流程链接去重** |
| 动态分区 | 按天自动建/删分区，冷热数据生命周期自动管理 |
| 物化视图 / 预聚合 | 看板走预聚合，不再实时扫明细 |
| 倒排索引（支持中文分词） | 关键词/全文检索可下沉 Doris，**可选替代一套 ES** |
| 多副本 + FE 高可用 | 生产可做到无单点 |
| 存算分离（3.x） | 大容量下降低存储成本 |

### 4.3 MySQL 与 Doris 的职责边界

**判据**：写少改少 / 只增不改 / 体量大 / 聚合多 → **Doris**；有事务 / 状态机 / 频繁更新 / 小体量配置 → **MySQL**。

| 数据 | 归属 | 理由 |
|---|---|---|
| `sys_*`（用户/角色/菜单/部门/字典/日志） | MySQL | 若依基座，强事务 |
| `yq_task` `yq_keyword` `yq_keyword_group` `yq_channel` `yq_noise_rule` `yq_alert_rule` `yq_push_rule` `yq_push_template` `yq_report_template` `yq_report_section` `yq_level_rule` | MySQL | 配置型、体量小、频繁增删改 |
| `yq_alert`（预警记录+处置状态） | MySQL | 状态机、频繁更新 |
| `yq_push_record`（推送记录） | MySQL | 状态机、重试更新 |
| `yq_report`（报告元信息+状态） | MySQL | 事务、状态流转 |
| `yq_knowledge` `yq_model_version` `yq_train_sample` | MySQL | 体量可控、需事务 |
| `yq_wecom_command` | MySQL | 体量小 |
| **`yq_opinion`（舆情主表）** | **Doris** | 事实核心，亿级，多维聚合 |
| **`yq_opinion_analysis`（研判宽表）** | **Doris** | 亿级，分析主入口 |
| **`yq_opinion_metric`（互动快照）** | **Doris** | 千万级滚动，仅追加 |
| **`yq_opinion_tag` / `yq_tag`** | **Doris**（标签定义可留 MySQL） | 关联明细体量大 |
| **`yq_opinion_cluster`（事件聚合）** | **Doris** | 聚合结果，分析用 |
| **`yq_collect_log`（采集日志）** | **Doris** | 量级 ≥ 主表 |
| **`yq_stats_daily`（统计预聚合）** | **Doris**（DWS/ADS） | 预聚合，看板数据源 |

> ⚠️ 跨库不做事务一致性，采用**最终一致 + 状态补偿**：MySQL 存状态与业务 ID，Doris 存事实明细；以 `opinion_id` / `url_hash` 关联。

### 4.4 Doris 数据仓库分层

| 层 | 库名 | 内容 | 写入方式 |
|---|---|---|---|
| ODS | `yq_ods` | 原始采集数据（未净化） | Stream Load |
| DWD | `yq_dwd` | 净化+去重后明细（Unique Key） | Stream Load / 定时 Insert Into |
| DWS | `yq_dws` | 按天×渠道×情感×风险预聚合 | 定时任务 / 物化视图 |
| ADS | `yq_ads` | 看板/报表专用宽表 | 定时任务 |

### 4.5 Doris 建表设计（示例 DDL）

**① 舆情主表（Unique Key on `url_hash`，动态按天分区）**

```sql
CREATE DATABASE IF NOT EXISTS yq_dwd;

CREATE TABLE yq_dwd.yq_opinion (
    url_hash        VARCHAR(64)   NOT NULL  COMMENT '链接SHA-256，唯一去重主键',
    opinion_id      BIGINT        NOT NULL  COMMENT '业务ID',
    task_id         BIGINT        NULL      COMMENT '监测任务ID',
    channel_id      BIGINT        NULL      COMMENT '采集渠道ID',
    title           VARCHAR(500)  NULL      COMMENT '标题',
    content         STRING        NULL      COMMENT '正文',
    opinion_url     VARCHAR(2000) NULL      COMMENT '原文链接',
    author          VARCHAR(200)  NULL      COMMENT '作者',
    region          VARCHAR(50)   NULL      COMMENT '地域',
    device          VARCHAR(50)   NULL      COMMENT '设备',
    topic_tags      STRING        NULL      COMMENT '话题标签(逗号分隔)',
    publish_time    DATETIME      NULL      COMMENT '发布时间',
    collect_time    DATETIME      NULL      COMMENT '采集时间',
    collect_date    DATE          NOT NULL  COMMENT '分区列=采集日期',
    senti_attr      VARCHAR(20)   NULL      COMMENT '情感属性',
    risk_level      VARCHAR(20)   NULL      COMMENT '风险等级',
    clean_status    VARCHAR(20)   NULL      COMMENT '净化状态',
    analyze_status  VARCHAR(20)   NULL      COMMENT '研判状态',
    cluster_id      BIGINT        NULL      COMMENT '事件聚合ID',
    INDEX idx_title   (title)   USING INVERTED PROPERTIES("parser"="chinese"),
    INDEX idx_content (content) USING INVERTED PROPERTIES("parser"="chinese")
)
UNIQUE KEY(url_hash)
PARTITION BY RANGE(collect_date) ()
DISTRIBUTED BY HASH(url_hash) BUCKETS 16
PROPERTIES (
    "replication_allocation"          = "tag.location.default: 3",
    "enable_unique_key_merge_on_write" = "true",
    "dynamic_partition.enable"        = "true",
    "dynamic_partition.time_unit"     = "DAY",
    "dynamic_partition.start"         = "-1095",   -- 保留 3 年
    "dynamic_partition.end"           = "3",
    "dynamic_partition.prefix"        = "p",
    "dynamic_partition.buckets"       = "16"
);
```

### 4.6 数据同步链路（无消息队列 · Stream Load 直写）

| 方案 | 链路 | 适用 | 取舍 |
|---|---|---|---|
| **A（采用）** | 采集 Worker → 本地有界队列 + 磁盘暂存 → 批量攒批 → **Doris Stream Load** | 采集/研判主链路 | 链路最短、无外部中间件；削峰靠有界队列 + 本地暂存文件 |
| B | 先写 MySQL → 定时 `Insert Into … Select` 同步 Doris | 配置类/小表/日汇总 | 简单、有延迟 |
| C | Stream Load 开启 **Group Commit**（2.1+） | 高频小批写入 | 降低小批量事务开销，适合低延迟场景 |

**为什么可以不要 Kafka**：Doris Stream Load 本身是 HTTP 批量原子导入，单 BE 吞吐可达数十 MB/s；配合「有界队列 + 批量攒批（如 5s / 1000 条）」即可满足日均 5 万条、峰值 500 条/分的量级。去掉 MQ 后组件更少、部署更简单。

**需要补齐的（Kafka 原本提供的能力）**：①削峰 → 有界阻塞队列 + 本地磁盘暂存；②失败回放 → 暂存批次文件保留 24~72h 定时重投；③多消费者 → 采集与研判 Worker 各自读源，必要时用 Redis Stream 做轻量补偿通道。

**Stream Load 写入示例**：

```http
PUT /api/yq_dwd/yq_opinion/_stream_load
Authorization: Basic {base64(user:pass)}
label: yq_dwd_yq_opinion_{yyyyMMddHHmmss}_{batchNo}
format: json
strip_outer_array: true
jsonpaths: ["$.urlHash","$.opinionId","$.title","$.collectDate"]

[ {"urlHash":"9f2c...","opinionId":1761400000000000001,
   "title":"示例标题","collectDate":"2026-09-18"} ]
```

写入要点：**label 幂等**（同 label 重复导入自动去重，天然补偿重试）；**Unique Key(url_hash)** 让重复链接 upsert 覆盖；失败按返回体 `Status` 与 `ErrorURL` 定位脏数据。

> 配置类数据（规则、模板、任务）**不落 Doris**，需要时在查询侧与 MySQL 关联；Doris 侧只增不改。

### 4.7 检索归属（已确认：Doris 倒排索引）

- **方案一：Doris 倒排索引**——一套组件搞定明细检索与聚合，省运维；中文用 `parser=chinese`。
- **方案二：独立 Elasticsearch**——检索能力更强（相关度、分词、聚合多样），但多一套集群要维护。
- ✅ **已确认采用方案一**：中文分词倒排索引下沉 Doris，**不引入独立 ES**，对齐 PRD「全文检索 100 万条 <1s」；若后续检索场景复杂化（相关度排序、多字段高亮、日志检索）再评估引入 ES。

### 4.8 Doris 集群规划（已确认：自建集群）

| 环境 | FE | BE | 规格建议 |
|---|---|---|---|
| 开发/测试 | 1 | 1（可与 FE 混部） | 8C16G + SSD 500G |
| 生产（起步） | **3**（高可用） | **3** | 每节点 8C32G + SSD 1T，`replication_num=3` |
| 生产（规模化） | 3 | 5~7（或存算分离） | 按实测数据量线性扩 BE；冷数据可下沉对象存储 |

> Doris 与 MySQL/Redis 分机部署，**独占磁盘 IO**；BE 数据盘用 SSD。

## 5. 数据采集技术方案（详述）

> 本章回答两个问题：**用什么技术爬**、**遇到反爬怎么处理**。采集是全链路的数据源头，其稳定性直接决定研判与预警的质量上界。

### 5.1 先给源分档：不同难度用不同通道

| 档 | 源类型 | 典型站点 | 抓取通道 | 难度 |
|---|---|---|---|---|
| **A** | 静态 HTML | 新闻门户、政务网站、地方媒体 | HttpClient5 + Jsoup 直连解析 | 低 |
| **B** | 动态渲染 SPA | 微博、部分资讯站、H5 站点 | Playwright 无头渲染后取 DOM | 中 |
| **C** | 开放接口 / RSS / 授权 API | 有官方接口的平台、搜索聚合 | 直连 JSON API | 低（最稳最合规） |
| **D** | 移动端 APP 接口 | 新闻客户端、短视频 | 抓包还原接口（**须公开或已授权**） | 高 |

> **选通道优先级**：能用官方接口就不解析页面，能用静态解析就不上无头浏览器。越靠前越稳、越快、越省资源，也越不容易触发风控。

### 5.2 采集引擎技术选型

| 能力 | 选型 | 说明 |
|---|---|---|
| HTTP 客户端 | **Apache HttpClient 5**（连接池 + HTTP/2）/ OkHttp 4 | 主力抓取器，连接复用、超时重试可配 |
| HTML 解析 | **Jsoup 1.17+** | CSS 选择器提取，容错解析脏 HTML |
| JSON 解析 | Jackson + Jayway JsonPath | 接口类数据源的字段定位 |
| 动态渲染 | **Playwright for Java**（首选）/ Selenium 4 | 无头 Chromium，等 `networkidle` 后再取 DOM |
| 正文智能提取 | **crux（Java 版 Readability）** / Boilerpipe | 站点无固定模板时兜底抽正文，降低适配成本 |
| 定时调度 | **SnailJob**（若依 v6 内置） | 分布式调度 + 分片广播，采集任务集中编排 |
| 快照留存 | **MinIO** | 落地 HTML 原文 / 截图，便于回溯取证 |
| 去重主键 | **链接 SHA-256**（`url_hash`） | 与 Doris Unique Key 天然对齐（见 §4.5） |
| 采集框架 | **自研站点适配器引擎**（借鉴 webmagic 分层思想） | 不直接引第三方爬虫框架：需与若依任务/字典/日志/权限打透 |

**自研引擎分层**（与若依生态对齐）：

```text
CollectWorker（独立进程，可水平扩展）
  └─ Scheduler      任务编排：关键词 × 渠道 × 频次，SnailJob 触发 + 分片
      └─ Downloader 下载器：静态 / 渲染双通道，统一输出 HTTP 响应或 DOM
          └─ ProxyProvider  代理池 + Cookie 池供给
      └─ Parser     解析器：选择器规则 / JSONPath → 统一 OpinionDTO
      └─ Pipeline   清洗 → 去重 → 快照落 MinIO → 攒批 Stream Load 入 Doris
```

### 5.3 站点适配器（SiteAdapter）：把"每站怎么写"变成配置

新站点接入**不改代码**。适配器以配置化规则描述列表页、字段选择器、时间格式，存 MySQL 的渠道配置表，后台可视化维护：

```yaml
code: DEMO_NEWS
channelName: 某新闻网站
entryType: static                # static | render | api
listUrl: "https://news.example.com/search?q={kw}&p={page}"
pageRule: { start: 1, size: 20, maxPage: 5 }
listItemSelector: "div.result-item"
fields:
  title:       { selector: "h3 a", attr: text }
  opinionUrl:  { selector: "h3 a", attr: href, prefix: "https://news.example.com" }
  publishTime: { selector: "span.time", attr: text, pattern: "yyyy-MM-dd HH:mm" }
detailRule:
  contentSelector: "div.article-content"
  pageNum: 3                     # 详情翻页
antiBot: { useProxy: true, minIntervalMs: 1500, maxIntervalMs: 4000 }
```

> 站点改版导致采集失效时，后台改选择器即可恢复，**无需发版**——这是采集长期可运维的关键。

### 5.4 采集调度模型

| 机制 | 做法 |
|---|---|
| 任务矩阵 | `关键词组 × 渠道 × 频次` 生成任务；热点/预警词分钟级，长尾词小时级/天级 |
| 增量水位线 | 按渠道记 `last_collect_time`，只抓新内容；翻页遇到"全部早于水位线"即停 |
| 分片执行 | 同一渠道的多个关键词分片下发到不同 Worker，避免单点串行 |
| 优先级 + 限流 | Redis 令牌桶按渠道配 QPS，热点任务提权 |
| 幂等 | `url_hash` 唯一键 + Stream Load `label`，重复抓取自动吸收（见 §4.6） |

### 5.5 反爬对抗（核心）

反爬本质是"特征识别 vs 特征伪装"的对抗。正确姿势是**先识别被拦信号，再按层匹配对抗手段**，而不是一上来就上无头浏览器。

#### 5.5.1 第一步：判断"是否被拦"

| 被拦信号 | 含义 |
|---|---|
| HTTP 403 / 429 / 503 | 直接拒绝或被限流 |
| 200 但内容为空 / 仅返回 JS 壳 | 需渲染，或已进风控页 |
| 跳转验证码页 / 滑块页 | 触发人机校验 |
| 连接重置 / TLS 握手失败 | IP 或 TLS 指纹被拉黑 |
| 返回内容与关键词完全无关 | 蜜罐页或降级内容 |

采集端统一封装 `BlockDetector`：命中即把该「渠道 × 代理」标记异常，转入对抗策略，并计入监控。

#### 5.5.2 反爬手段 → 对抗方案对照表

| 站点反爬手段 | 识别特征 | 对抗方案 | 组件 |
|---|---|---|---|
| **IP 频次限制 / 封禁** | 403、429、连接重置 | 代理池轮换 IP + 按站点降频 + 多出口分散 | 自研代理池 |
| **UA / Referer / Header 校验** | 403 或空壳 | 真实浏览器 Header 库随机轮换，补全 Referer 链、Accept-Language | HeaderPool |
| **Cookie / Session 校验** | 跳登录、验证码 | Cookie 池 + 定时保活探活 | CookiePool |
| **TLS 指纹（JA3/JA4）** | TLS 握手被拒 | curl-impersonate 或 Bouncy Castle 定制 ClientHello，模拟 Chrome 指纹 | HttpClient 定制 |
| **浏览器指纹（WebGL/Canvas/字体/时区）** | 一渲染就风控页 | Playwright + stealth 注入（隐藏 `navigator.webdriver`、伪造 GPU/字体/时区/语言） | Playwright |
| **JS 渲染 + 加密参数（sign/token）** | 静态页无数据 | Playwright 渲染取真实 DOM；必要时 JS 逆向（AST 还原 + 补环境） | Playwright / 逆向 |
| **图形验证码** | 出现验证码图 | OCR（ddddocr）优先，失败转打码平台兜底 | 打码服务 |
| **滑块 / 点选验证码** | 滑块组件 | 缺口识别 + 拟人轨迹（带加速度曲线）拖动；高难转打码 | 打码服务 |
| **行为风控（轨迹、点击频率）** | 风控页 | 拟人化：随机延时、贝塞尔轨迹、随机滚动 | Playwright |
| **频率算法限制** | 429 | 令牌桶限速 + 请求间隔**随机化**（非固定间隔）+ 采集时段分散 | RateLimiter |
| **蜜罐链接 / 陷阱字段** | 内容异常 | 黑白名单 + 内容异常检测（长度/关键词命中率） | Pipeline |
| **登录墙 / 付费墙** | 跳登录 | **不破解**：改用已授权账号或公开摘要（合规红线，见 §5.8） | — |

#### 5.5.3 三级对抗策略（按成本递进）

```text
Level 1  轻量伪装 —— 覆盖约 70% 站点，成本最低
  HttpClient5 + Header 轮换 + 代理池轮换 + 随机延时
        │ 仍被拦
Level 2  指纹修正 —— 覆盖约 20%（中等风控站点）
  curl-impersonate 修正 TLS 指纹 + Cookie 池保活 + 令牌桶降频
        │ 仍被拦
Level 3  无头浏览器 + 拟人化 —— 覆盖约 10%（高风控站点）
  Playwright stealth 渲染 + 拟人轨迹 + 验证码 OCR/打码 + 站点专属优质代理
```

> **不做的事**：不攻击站点、不绕过付费墙、不冒用身份获取非公开数据、不以高并发压垮对方服务。反爬对抗的目标是"稳定获取公开信息"，不是"攻破防线"。

#### 5.5.4 对抗的调度与降级

| 机制 | 说明 |
|---|---|
| 渠道健康度评分 | 成功率 / 响应时间 / 被封次数 → 评分衰减，自动降频或暂停 |
| 代理分级 | 优质池（保高风控站点）、通用池、备用池，按渠道绑定 |
| 降级链 | 主通道被拦 → 渲染通道 → 备用同源站点 → 搜索摘要补充 → 告警留痕 |
| 低峰提权 | 站点低负载时段提高频次，降低被封概率 |

### 5.6 自研代理池设计

| 模块 | 设计 |
|---|---|
| 来源 | 商业代理 API（短效动态 IP）+ 自建拨号/VPS 节点（PPPoE 换 IP） |
| 健康检查 | 定时以目标站点探活，记录可用性/延迟/被封率并评分排序 |
| 分级 | 优质 / 通用 / 备用三级，按渠道绑定最低等级 |
| 使用 | 按策略取 IP（轮换 or 粘性会话），失败自动摘除 |
| 会话 | 支持"粘性 IP"：同一会话保持出口 IP，兼容 Cookie 校验类站点 |
| 成本控制 | 按渠道配置代理配额，超限告警，防止跑爆 |

### 5.7 解析、清洗与入库衔接

| 环节 | 做法 |
|---|---|
| 字段提取 | 标题、正文、作者、发布时间、来源、链接、阅读/转发量（有则取） |
| 清洗 | 去广告/导航/评论噪声 → HTML 转纯文本 → 时间归一化 → 编码与全半角统一 |
| 快照 | HTML 原文 + 关键截图存 MinIO，保留 ≤30 天（对齐 PRD），供溯源复核 |
| 去重 | `url_hash = SHA-256(归一化链接)`，跨渠道跨批次全局去重（明细级） |
| 入库 | 攒批（5s / 1000 条）→ Doris Stream Load → ODS/DWD（见 §4.6） |

### 5.8 合规与采集边界（必须遵守）

| 项 | 约束 |
|---|---|
| 采集范围 | 仅采**公开**信息；不采个人隐私，不采需登录且未授权的数据 |
| robots.txt | 遵守站点 robots 与使用条款；有授权接口的一律走授权接口 |
| 频控 | 单站点 QPS 受控，不造成对方服务压力；禁止压测式抓取 |
| 身份 | 不伪造、不冒用他人身份；不破解登录墙与付费墙 |
| 数据用途 | 仅用于内部监测研判报送；原文与快照按合规要求留存与销毁 |
| 模型调用 | 送大模型前做敏感字段脱敏（作者/地域），遵守 §9 安全约束 |

### 5.9 采集可观测指标

| 指标 | 用途 |

| 采集成功率 / 渠道失败率 | 渠道健康度，触发降频或停采 |
| 单渠道条数骤降 | 站点改版或被封的早期信号 |

| 适配器失效率 | 触发选择器维护 |

## 9. 安全设计（对齐 PRD §3.2，补数据层）

- 接口权限：全部 `@SaCheckPermission("yuqing:xxx:xxx")`；数据行权限复用 `@DataScope` 扩展为按任务/渠道/部门过滤。
- 参数安全：`@RequestBody` 加 `@Validated`；自由文本加 `@Xss`；采集正文**禁止 `v-html` 直渲**。
- 凭据管理：企业微信 CorpId/Secret/AgentId、大模型 API Key、代理池账号**加密存储**（配置中心/加密字段），禁止硬编码与入库明文。
- 文件：仅 MinIO 存文件，DB 存 URL；访问走鉴权或带有效期签名 URL；导入仅 `.xlsx/.xls` 且 ≤10MB。
- 操作审计：CUD、规则变更、报告提交、权限变更、导出、导入全部 `@Log`。
- **Doris 侧新增**：Doris 仅开放内网访问；业务侧使用**只读账号**查 Doris，写入由 Stream Load 专用账号执行；敏感字段（作者、地域）在 ODS→DWD 做脱敏映射，大模型调用前脱敏。

## 附录 A：与 PRD 的差异点（需同步更新 PRD）

引入 Doris 后，PRD 以下内容需同步修订：

1. **§3.3 兼容性**「数据库: MySQL 8.0+」应补充为「MySQL 8.0+（事务库）+ Apache Doris 2.1/3.0（分析库）」。
2. **§5 数据模型**：`yq_opinion` 等事实表的存储归属需标注为 Doris，并补 Doris 建表 DDL（见 §4.5）。
3. **§6.3 API 约定**：涉及 Doris 的聚合查询接口需注明走 `@DS("doris")` 数据源。
4. **§7 权限矩阵**：新增 Doris 只读账号与 Stream Load 专用写入账号的权限约定。
5. **§3.3 中间件**：若 PRD 提及消息队列，需删除（本架构不使用 Kafka / RocketMQ）。
