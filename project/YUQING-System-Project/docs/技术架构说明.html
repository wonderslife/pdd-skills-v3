1架构目标与设计原则

1.1 目标

目标落地要求
海量数据可分析年增舆情 ≤ 2000 万条、保留 3 年；多维聚合（渠道×情感×风险×时间×地域×任务）秒级返回
全流程自动化采集→净化→研判→预警→推送→出报，人工仅参与规则配置与结果复核
双端一体PC 管理端（Vue3）+ 企业微信内嵌 H5（uniapp），共用若依账号体系
复用不重造用户 / 角色 / 菜单 / 部门 / 字典 / 操作日志 / 定时任务直接复用若依基座
可水平扩展采集与研判是高并发异步任务，按 Worker 独立扩，不拖垮业务 API

1.2 五条设计原则

  1. 事务与分析分离——MySQL 只承接事务型 / 配置型 / 状态机型数据，海量事实与聚合下沉 Doris，禁止在 MySQL 对千万级表做多维聚合。
  2. 写路径异步化——采集与入库在 Worker 内异步解耦，批量攒批后写入，不阻塞在线请求。
  3. 读路径预聚合——看板 / 报表读 Doris 物化视图或 DWS / ADS 预聚合表，不实时扫明细。
  4. 能复用不新建——权限、字典、日志、定时、代码生成全部走若依内置能力。
  5. 模块化单体起步，任务节点独立扩——不过早拆微服务；采集 / 研判 / 推送 / 报告以独立进程运行，共享领域代码。

本次变更（v0.4）：新增 §5 数据采集技术方案（详述）——抓取通道分档、采集引擎分层与站点适配器配置化、反爬对抗矩阵与三级策略、自研代理池、合规边界与可观测指标。上版起已移除 Kafka，采集侧直接调用 Doris Stream Load 批量写入。

4数据库架构（MySQL + Doris 双库）

4.1 为什么舆情数据要单独走 Doris

数据量论证（对齐 PRD §3.1「年增 ≤ 2000 万条、快照保留 ≤ 30 天」）：

数据量级估算
yq_opinion 舆情主表年增 ~2000 万，保留 3 年 → ~6000 万行
yq_opinion_analysis 研判结果与主表 1:1，宽表 → ~6000 万行
yq_opinion_metric 互动快照日粒度保留 30 天，按活跃舆情展开 → 千万级滚动
yq_collect_log 采集日志按批次×渠道，量级 ≥ 主表，保留期长
标签关联 / 聚类 / 统计百万 ~ 千万级
合计亿级行、TB 级存储

查询特征是多维交叉聚合（渠道×情感×风险×地域×时间×任务）、TOP 榜、趋势曲线、关键词检索——这类 OLAP 负载在 MySQL 千万级之后明显劣化（无列存、无向量化、无 MPP）。因此舆情事实数据独立建库建表落 Apache Doris。

4.2 Doris 的选型优势

能力对本案的价值
MPP + 列存 + 向量化执行亿级聚合秒级返回，看板 / 报表不卡
MySQL 协议兼容JDBC 直连，复用 MyBatis / dynamic-datasource，学习成本低
Unique Key 模型（MoW）以 url_hash 为主键 upsert，天然承接全流程链接去重
Stream Load 导入HTTP 批量原子导入，高吞吐，无需消息队列即可实时入仓
动态分区按天自动建 / 删分区，冷热生命周期自动管理
物化视图 / 预聚合看板走预聚合，不实时扫明细
倒排索引（中文分词）关键词 / 全文检索可下沉 Doris，可选替代一套 ES
多副本 + FE 高可用生产可做到无单点

4.3 MySQL 与 Doris 的职责边界

判据：写少改少 / 只增不改 / 体量大 / 聚合多 → Doris；有事务 / 状态机 / 频繁更新 / 小体量配置 → MySQL。

数据归属理由
sys_*（用户 / 角色 / 菜单 / 部门 / 字典 / 日志）MySQL若依基座，强事务
yq_task yq_keyword yq_keyword_group yq_channel yq_noise_rule yq_alert_rule yq_push_rule yq_push_template yq_report_template yq_report_section yq_level_ruleMySQL配置型、体量小、频繁增删改
yq_alert 预警记录（含处置状态）MySQL状态机、频繁更新
yq_push_record 推送记录MySQL状态机、重试更新
yq_report 报告元信息MySQL事务、状态流转
yq_knowledge yq_model_version yq_train_sampleMySQL体量可控、需事务
yq_opinion 舆情主表Doris事实核心，亿级，多维聚合
yq_opinion_analysis 研判宽表Doris亿级，分析主入口
yq_opinion_metric 互动快照Doris千万级滚动，仅追加
yq_opinion_tag / yq_tagDoris关联明细体量大（标签定义可留 MySQL）
yq_opinion_cluster 事件聚合Doris聚合结果，分析用
yq_collect_log 采集日志Doris量级 ≥ 主表

跨库不做事务一致性，采用最终一致 + 状态补偿：MySQL 存状态与业务 ID，Doris 存事实明细；以 opinion_id / url_hash 关联。

4.6 数据同步链路（无消息队列 · Stream Load 直写）

方案链路适用取舍
A（采用）采集 Worker → 本地有界队列 + 磁盘暂存 → 批量攒批 → Doris Stream Load采集 / 研判主链路链路最短、无外部中间件；削峰靠有界队列 + 本地暂存文件
B先写 MySQL → 定时 Insert Into … Select 同步 Doris配置类 / 小表 / 日汇总简单、有延迟
CStream Load 开启 Group Commit（2.1+）高频小批写入降低小批量事务开销，适合低延迟场景

为什么可以不要 Kafka：Doris Stream Load 本身是 HTTP 批量原子导入，单 BE 吞吐可达数十 MB/s，配合「有界队列 + 批量攒批（如 5s / 1000 条）」即可满足日均 5 万条、峰值 500 条/分的量级。去掉 MQ 后组件更少、部署更简单。

需要补的能力（Kafka 原本提供）：①削峰 → 有界阻塞队列 + 本地磁盘暂存；②失败回放 → 暂存批次文件保留 24~72h，定时重投；③多消费者 → 采集与研判 Worker 各自读源，必要时用 Redis Stream 做轻量补偿通道。

Stream Load 写入示例

PUT /api/{db}/{table}/_stream_load
Authorization: Basic {base64(user:pass)}
Expect: 100-continue
label: yq_dwd_yq_opinion_{yyyyMMddHHmmss}_{batchNo}
format: json
strip_outer_array: true
jsonpaths: ["$.urlHash","$.opinionId","$.title","$.collectDate"]

[ {"urlHash":"9f2c...","opinionId":1761400000000000001,
   "title":"示例标题","collectDate":"2026-09-18"} ]
# 返回体（成功）
{
  "TxnId": 10001, "Label": "yq_dwd_yq_opinion_20260918103000_8812",

4.7 检索归属（已确认：Doris 倒排索引）

  • 方案一（采用）：Doris 倒排索引——一套组件搞定明细检索与聚合，省运维；中文用 parser=chinese。
  • 方案二：独立 Elasticsearch——检索相关度、分词、高亮更强，但多一套集群要维护与同步。

✅ 采用方案一：中文分词倒排索引下沉 Doris，不引入独立 ES，对齐 PRD「全文检索 100 万条 <1s」；后续若检索场景复杂化（相关度排序、多字段高亮、日志检索）再评估 ES。

4.8 Doris 集群规划（已确认：自建集群）

环境FEBE规格建议

5数据采集技术方案（详述）

本章回答两个问题：用什么技术爬、遇到反爬怎么处理。采集是全链路的数据源头，其稳定性直接决定研判与预警的质量上界。

5.1 先给源分档：不同难度用不同通道

档源类型典型站点抓取通道难度
A静态 HTML新闻门户、政务网站、地方媒体HttpClient5 + Jsoup 直连解析低
B动态渲染 SPA微博、部分资讯站、H5 站点Playwright 无头渲染后取 DOM中
C开放接口 / RSS / 授权 API有官方接口的平台、搜索聚合直连 JSON API低（最稳、最合规）
D移动端 APP 接口新闻客户端、短视频抓包还原接口（须公开或已授权）高

选通道优先级：能用官方接口就不解析页面，能用静态解析就不上无头浏览器——越靠前越稳、越快、越省资源，也越不容易触发风控。

5.2 采集引擎技术选型

能力选型说明
HTTP 客户端Apache HttpClient 5（连接池 + HTTP/2）/ OkHttp 4主力抓取器，连接复用、超时重试可配
HTML 解析Jsoup 1.17+CSS 选择器提取，容错解析脏 HTML
JSON 解析Jackson + Jayway JsonPath接口类数据源的字段定位
动态渲染Playwright for Java（首选）/ Selenium 4无头 Chromium，等 networkidle 后再取 DOM
正文智能提取crux（Java 版 Readability） / Boilerpipe站点无固定模板时兜底抽正文，降低适配成本
定时调度SnailJob（若依 v6 内置）分布式调度 + 分片广播，采集任务集中编排
快照留存MinIO落地 HTML 原文 / 截图，便于回溯取证
去重主键链接 SHA-256（url_hash）与 Doris Unique Key 天然对齐（见 §4.5）
采集框架自研站点适配器引擎（借鉴 webmagic 分层思想）不直接引第三方爬虫框架：需与若依任务 / 字典 / 日志 / 权限打透

自研引擎分层（与若依生态对齐）：

CollectWorker（独立进程，可水平扩展）
  └─ Scheduler      任务编排：关键词 × 渠道 × 频次，SnailJob 触发 + 分片
      └─ Downloader 下载器：静态 / 渲染双通道，统一输出 HTTP 响应或 DOM
          └─ ProxyProvider  代理池 + Cookie 池供给
      └─ Parser     解析器：选择器规则 / JSONPath → 统一 OpinionDTO
      └─ Pipeline   清洗 → 去重 → 快照落 MinIO → 攒批 Stream Load 入 Doris

5.3 站点适配器（SiteAdapter）：把「每站怎么写」变成配置

新站点接入不改代码。适配器以配置化规则描述列表页、字段选择器、时间格式，存 MySQL 渠道配置表，后台可视化维护：

code: DEMO_NEWS
channelName: 某新闻网站
entryType: static                # static | render | api
listUrl: "https://news.example.com/search?q={kw}&p={page}"
pageRule: { start: 1, size: 20, maxPage: 5 }
listItemSelector: "div.result-item"
fields:
  title:       { selector: "h3 a", attr: text }
  opinionUrl:  { selector: "h3 a", attr: href, prefix: "https://news.example.com" }

5.5 反爬对抗（核心）

反爬本质是「特征识别 vs 特征伪装」的对抗。正确姿势是先识别被拦信号，再按层匹配对抗手段，而不是一上来就上无头浏览器。

5.5.1 第一步：判断「是否被拦」

被拦信号含义
HTTP 403 / 429 / 503直接拒绝或被限流
200 但内容为空 / 仅返回 JS 壳需渲染，或已进风控页
跳转验证码页 / 滑块页触发人机校验
连接重置 / TLS 握手失败IP 或 TLS 指纹被拉黑
返回内容与关键词完全无关蜜罐页或降级内容

采集端统一封装 BlockDetector：命中即把该「渠道 × 代理」标记异常，转入对抗策略，并计入监控。

5.5.2 反爬手段 → 对抗方案对照表

站点反爬手段识别特征对抗方案组件
IP 频次限制 / 封禁403、429、连接重置代理池轮换 IP + 按站点降频 + 多出口分散自研代理池
UA / Referer / Header 校验403 或空壳真实浏览器 Header 库随机轮换，补全 Referer 链、Accept-LanguageHeaderPool
Cookie / Session 校验跳登录、验证码Cookie 池 + 定时保活探活CookiePool
TLS 指纹（JA3/JA4）TLS 握手被拒curl-impersonate 或 Bouncy Castle 定制 ClientHello，模拟 Chrome 指纹HttpClient 定制
浏览器指纹（WebGL / Canvas / 字体 / 时区）一渲染就风控页Playwright + stealth 注入（隐藏 navigator.webdriver、伪造 GPU / 字体 / 时区 / 语言）Playwright
JS 渲染 + 加密参数（sign / token）静态页无数据Playwright 渲染取真实 DOM；必要时 JS 逆向（AST 还原 + 补环境）Playwright / 逆向
图形验证码出现验证码图OCR（ddddocr）优先，失败转打码平台兜底打码服务
滑块 / 点选验证码滑块组件缺口识别 + 拟人轨迹（带加速度曲线）拖动；高难转打码打码服务
行为风控（轨迹、点击频率）风控页拟人化：随机延时、贝塞尔轨迹、随机滚动Playwright
频率算法限制429令牌桶限速 + 请求间隔随机化（非固定间隔）+ 采集时段分散RateLimiter
蜜罐链接 / 陷阱字段内容异常黑白名单 + 内容异常检测（长度 / 关键词命中率）Pipeline
登录墙 / 付费墙跳登录不破解：改用已授权账号或公开摘要（合规红线，见 §5.8）—

5.5.3 三级对抗策略（按成本递进）

Level 1  轻量伪装 —— 覆盖约 70% 站点，成本最低
  HttpClient5 + Header 轮换 + 代理池轮换 + 随机延时
        │ 仍被拦
Level 2  指纹修正 —— 覆盖约 20%（中等风控站点）
  curl-impersonate 修正 TLS 指纹 + Cookie 池保活 + 令牌桶降频
        │ 仍被拦
Level 3  无头浏览器 + 拟人化 —— 覆盖约 10%（高风控站点）
  Playwright stealth 渲染 + 拟人轨迹 + 验证码 OCR / 打码 + 站点专属优质代理

不做的事：不攻击站点、不绕过付费墙、不冒用身份获取非公开数据、不以高并发压垮对方服务。反爬对抗的目标是「稳定获取公开信息」，不是「攻破防线」。

5.5.4 对抗的调度与降级

机制说明
渠道健康度评分成功率 / 响应时间 / 被封次数 → 评分衰减，自动降频或暂停
代理分级优质池（保高风控站点）、通用池、备用池，按渠道绑定
降级链主通道被拦 → 渲染通道 → 备用同源站点 → 搜索摘要补充 → 告警留痕
低峰提权站点低负载时段提高频次，降低被封概率

5.6 自研代理池设计

模块设计

健康检查定时以目标站点探活，记录可用性 / 延迟 / 被封率并评分排序
分级优质 / 通用 / 备用三级，按渠道绑定最低等级

9安全设计（对齐 PRD §3.2，补数据层）

  • 接口权限：全部 @SaCheckPermission("yuqing:xxx:xxx")；数据行权限复用 @DataScope 扩展为按任务 / 渠道 / 部门过滤。
  • 参数安全：@RequestBody 加 @Validated；自由文本加 @Xss；采集正文禁止 v-html 直渲。
  • 凭据管理：企业微信 CorpId / Secret / AgentId、大模型 API Key、代理池账号加密存储，禁止硬编码与入库明文。
  • 文件：仅 MinIO 存文件，DB 存 URL；访问走鉴权或带有效期签名 URL；导入仅 .xlsx/.xls 且 ≤ 10MB。
  • 操作审计：CUD、规则变更、报告提交、权限变更、导出、导入全部 @Log。
  • Doris 侧新增：Doris 仅开放内网访问；业务侧用只读账号查询，写入由 Stream Load 专用账号执行；敏感字段（作者、地域）在 ODS→DWD 脱敏映射，大模型调用前脱敏。
