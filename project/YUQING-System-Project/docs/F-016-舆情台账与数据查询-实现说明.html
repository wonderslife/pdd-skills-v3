一、开工前的摸底结论

F-016 与前几个功能不同：它几乎没有新表、没有新实体。台账展示的就是 F-004 采集、F-006 清洗、F-007 研判之后的 yq_opinion 及其关联数据。所以本功能的工作量不在「存」，而在「查得准、查得快、查得安全、导得出」四件事。

先摸清四件事才动手：

检查项现状处置
yq_opinion 及关联表F-004/F-006 已建，含溯源字段、互动数据、研判字段不动 SQL，只加索引
台账审计表不存在（PRD §5.2 有定义，schema 未建）新增 yq_ledger_export_log（19 列）+ 2 索引
YqOpinionController不存在（主生成器对 opinion 表声明 ctrl:false）由本功能新建
事件聚合能力yq_opinion_cluster 表已有，但无查询服务新建 ClusterView + 时间轴判定
导出能力v6 只提供 Fesod（Excel），无字段裁剪与异步分流新建 LedgerExcelWriter + 同步/异步分流
异步调度SnailJob 已用于 F-004 / F-010 / F-014直接复用，不引新调度器
核心结论：F-016 的难点是「可见范围」和「导出边界」。 台账是全平台数据的总出口 —— 一旦数据权限写漏，就是把全公司舆情摊在每个人面前； 一旦导出上限写漏，就是一次请求把 20 万行塞进内存。这两处是本功能的安全重心。

二、三个架构决策（开工前已定）

#决策选型理由
①数据源A：@DS("doris") 段指向同一 MySQL 库现状 Doris 未就绪，但保留 @DS 注解 = 未来切 Doris 零改代码
②异步导出A：复用 SnailJob与 F-004/F-010/F-014 同一条链路，运维只需认识一个调度台
③数据权限A：按 yq_task.create_by 任务归属隔离舆情天然归属某个采集任务，任务归属是最自然的隔离维度
决策 ③A 的一个副作用必须记牢：PRD §7.3 说「舆情主管可见全部」， 但没规定角色 key 叫什么。硬编码任一 key 都会在客户环境静默失效 （现象是「主管只能看到自己的任务」，且不报任何错）。因此做成配置 yuqing.ledger.all-data-role-keys，默认空 = 只有超管看全量—— 漏配的后果是「少看」而不是「多看」。

六、台账查询数据流

① 请求 GET /yuqing/opinion/list?collectBeginTime=…&taskId=…&keyword=… │ ▼ ② 身份 → 可见范围（唯一可信来源，请求体无法扩大） LoginHelper.getUserId() ──► LedgerScopeResolver.resolve( superAdmin, hasAllDataRole(), ← 读配置 all-data-role-keys metaDao.ownedTaskIds(userId) ← yq_task.create_by ) ├─ all() 超管 / 全量角色 ──► 不加范围条件 ├─ none() 无授权任务 ──► eq(opinionId, -1L) ← 恒假条件，不是「不加条件」 └─ ofTasks() 普通用户 ──► in(taskId, 名下任务集) │ ▼ ③ 条件装配 LedgerWrapperFactory.applyFilters() 时间区间(采集/发布) / 任务 / 渠道 / 舆情属性 / 风险等级 / 舆情分级 / 传播层级 / 采集来源 / 清洗状态 / 研判状态 / 预警标记 / 标签 / 关键词 / 聚合事件 │ ▼ ④ 排序 applyOrder() — 白名单字段，杜绝前端传任意列名 │ ▼ ⑤ 分页 maxPageSize 硬上限（默认 200，防 pageSize=999999 拖库） │ ▼ ⑥ 组装 LedgerPage rows + total + hints（空态建议）+ scopeDesc + activeConditions
「none() 必须落成恒假条件」这条被写进了校验器。 none() 若实现成「不追加任何条件」，语义就从「拒绝一切」变成「放行一切」—— 这是最典型的越权写法，且肉眼几乎看不出来。 校验器 [14.5] 直接断言源码里必须出现 eq(YqOpinion::getOpinionId, -1L)。

九、两个刻意的安全设计

设计 1：XSS 防线在服务端，不在前端

检索高亮要把命中词包进 <em class="yq-hit">，前端用 v-html 渲染。 这意味着服务端必须保证这段 HTML 只含自己的标签。做法是「先转义、再插标记」：

highlight(text, keyword):
  1. escapeHtml(text)     ← & < > " ' 全部转义，原文里的标签变成字面量
  2. 在转义后的串上定位命中词并插入 <em class="yq-hit">
  → 恶意关键词（如 <img onerror=…>）也走同一转义，无法逃逸

详情正文则更保守：PC 端用 <pre>{{ detail.content }}</pre>，
连 v-html 都不用。校验器 [14.11] 直接断言这一点。

设计 2：越权探测防护

detail(opinionId) 不在可见范围内时 →
  返回统一话术「无权查看该舆情，或该舆情已不存在」
  ── 不区分「无权」与「不存在」──

理由：若两种情形返回不同文案，攻击者可用遍历 ID 的方式，
      通过响应差异探测出「哪些 ID 真实存在」，从而摸清他人数据规模。

十一、已知边界（不藏着）

  • F-016 未在真实数据量下端到端跑过：代码路径与自测全绿，但线上 yq_opinion 当前 0 行。检索性能（LIKE 全文）、导出 5000 条分流的实际耗时、Doris 切换后的行为，都需要有数据后复测。
  • 检索是 LIKE 而非全文索引：当前实现按标题/正文做 LIKE %kw%，符合「先看有没有、再进详情」的用法，但不适合超大数据量。切 Doris 后可换倒排索引，届时只需改 LedgerWrapperFactory.forSearch。
  • 异步导出的推送默认关闭：export-push-enabled=false。开启依赖 F-011 企微通道就绪（与 F-011/F-014 同一阻塞项：企微凭据）。关闭时用户需自行回「导出记录」取链接，不阻塞功能。
  • 调度台需手工建作业：@JobExecutor(name="yuqingLedgerExport") 已就位，但需在 SnailJob 控制台建作业并把 作业ID 填入 yuqing.ledger.export-job-id；未配则退化为进程内线程池（可用，但没有执行记录与人工补偿）。
  • 事件聚合依赖 F-007 产出：yq_opinion_cluster 的聚类结果由研判环节写入。ClusterView 与时间轴判定已完备，但 F-007 未实现前，事件聚合页无真实数据可看。
  • 数据权限严格程度依赖正确配置：默认仅超管可见全量。生产上线必须按实际角色键配置 all-data-role-keys，否则「舆情主管」会退化为「只能看自己名下任务」。
