一、四个架构决策与落地方式

决策点拍板结果理由与代价
聚合算在哪 Doris 预聚合
Unique Key + Merge-on-Write		 验收 8 要求「看板响应不随数据量增长而显著变慢」。同键重复写入即覆盖 ⇒ 重跑天然幂等， 不需要「先删后插」也不需要事务。代价：多 3 张 Doris 表 + 1 张批次台账表要维护。
聚合逻辑放哪 纯函数 StatsAggregator
不碰 DB、不碰 Spring		 定时任务与 PC「看板重算」共用同一份实现，杜绝「任务一套口径、手动一套口径」的数字漂移； 且能完全离线单测 —— 手搓几十条样本就覆盖了分桶、排序、归一、占比的全部分支。代价：明细必须一次性读进内存。
趋势曲线放哪 塞进 yq_stats_dim
dim_type='trend' + time_grain		 趋势本质上也是「某个时间桶的计数」，与分布同构。复用同一张表、同一套读写路径、同一个 Unique Key， 少一张表、少一套代码。代价：dim_key 语义随 dim_type 变化，读代码时需留意。
聚合失败了怎么办 批次台账留痕 + 降级展示
yq_stats_batch		 验收 9 要求「不影响主流程，展示最近一次成功聚合并标注截止时间」。所以批次先 begin 后 success， 失败写 fail_reason；看板读最近一次成功批次，把 data_until 与失败提示一并下发。 代价：看板可能展示「不是最新」的数据，因此必须在页面上显式标注，不能让人误判。

三、数据模型变更

3.1 新增 1 张 MySQL 表：yq_stats_batch（聚合批次台账）

共 15 个业务列 + 5 个审计列。它同时承担三件事：

列作用
batch_no / begin_date / end_date / trigger_type / status 批次身份与范围。trigger_type 取 auto / manual / replay（验收 8 的定时任务、手动重算、补算历史三态）。
source_count / daily_rows / dim_rows / hot_rows / cost_ms 产出规模与耗时，用于排查「聚合跑了但看板没数」这类问题。
data_until / notice / fail_reason 验收 9 的全部载体：数据截止时间、非致命提示（如明细命中上限被截断）、失败原因。
conclusion_json 验收 5 的载体：结构化分析结论（核心事件 / 传播路径 / 舆论焦点 / 风险点）以 JSON 落库， 类型 TEXT 而非 VARCHAR —— 结论体积随事件数增长，VARCHAR 迟早截断。

3.2 3 张 Doris 预聚合表（含 MySQL 镜像）

表Unique Key说明
yq_stats_daily(stats_date, task_id, channel_id) 日聚合：总量 / 正负面 / 去重剔除 / 降噪剔除 / 预警数 / 推送数 / 报告数 + 四项互动量（read_sum / comment_sum / share_sum / like_sum）+ negative_rate DECIMAL(5,2)。
yq_stats_dim(stats_date, dim_type, dim_key, time_grain, task_id, channel_id) 维度分布 + 趋势：dim_type 取 channel / region / topic / senti / risk / level / spread / trend 八类； time_grain 取 hour / day / week。
yq_stats_hot(stats_date, rank_by, rank_no) 热点榜：rank_by 取 read / share / comment / heat 四口径，各存当日 TopN。

为什么 negative_rate 用定点数而不是浮点：负面占比要落库、要进报表、要和阈值比较。 DECIMAL(5,2) 与 double 在「正好 30.00% 算不算超阈值」这类判断上结果不同，定点数没有这个歧义。 同理，热度打分 HeatScorer 全程 long 整数运算 —— 见 §4.3。

四、引擎设计

4.1 聚合流水线（YqAnalyticsServiceImpl.aggregate）

① ledger.begin(scope, trigger)            开批次，status=running，拿到 batch_no
② opinionReader.loadSlices(scope, 上限)   读 Doris 明细 → List<OpinionSlice>（命中上限则 truncated=true）
③ aggregator.aggregate(slices, scope, truncated)   ← 纯函数，一次遍历同时产出三张表
      ├─ buildDaily()  按 (collect_date, task_id, channel_id) 分桶
      ├─ buildDims()   八类维度 + 趋势三种粒度
      └─ buildHot()    每天 × 四口径 × TopN
④ mergeProcessMetrics(scope, outcome)     主库预警数/推送数按日"全量覆盖"进 daily 行（不是累加！）
⑤ conclusionExtractor.extract(slices, dim) 提炼结论 —— 必须在明细还在手里时做
⑥ 计算 dataUntil = 明细中最大发布时间
⑦（可选）purgeRange()                     先清该范围旧聚合行
⑧ statsWriter.write(outcome)              写 Doris 三张表（Unique Key 覆盖写）
⑨ ledger.success(batch, outcome, dataUntil, cost, conclusionJson)
  • 「先写数据、后标成功」的顺序是有意的：若第 ⑧ 步成功但第 ⑨ 步崩了，看板会认为最近批次失败而回退到上一次结果 —— 宁可少展示，不可展示半截数据。
  • ④ 必须是覆盖而非累加：daily 行由明细重算得出，流程量若累加，重跑一次就翻倍。这是幂等的另一半。
  • ④ 单独 try-catch：主库流程量读不到不拖垮整次聚合，主指标照常产出，只在 notice 里说明「相关列已置零」。
  • ⑤ 为什么不能在读看板时算：核心事件与传播路径需要逐条明细与时间序，看板只有预聚合行。所以结论产在聚合那一刻、存在批次上。

4.2 归属口径（这里最容易产生「数字对不上」的疑问）

指标归属依据后果
总量 / 正负面 / 分布类维度collect_date（采集日） 与 Doris 分区列一致，扫描最快。
趋势曲线publish_time（发布时间）
可配 trendByPublishTime=false 切回采集时间		 跨日传播时「曲线累计 ≠ 总量卡片」。这是设计内差异，不是 bug： 一条前天发布、今天采到的舆情，按发布日归到前天，按采集日归到今天。 看板把 trendBase 字段一并下发，由前端在图上标注口径。

时间缺失的记录只计入总量、不进曲线（addTrend 提前 return），避免伪造一个 0000-00-00 的桶。

4.3 热度打分（HeatScorer）

score = 阅读×1 + 评论×3 + 转发×5 + 点赞×1 + 内容热度分值×10（全部 long 整数运算）

权重逻辑是「主动行为高于被动浏览，转发权重最高」——转发是唯一能跨圈层扩散的动作。 为什么强制整数：热度既用于排序、又要落库、还要做报表；浮点在「相等则按时间倒序」的 tie-break 上会因精度抖动 导致同一天重跑名次变化，幂等直觉就没了。整数运算可复现，同输入必得同输出。

热点榜排序的 tie-break 显式三级：主指标降序 → 发布时间降序 → 舆情ID降序。 三级写完整才保证「同一天重跑名次不变」——单测 rankTopStableTieBreak 就是钉这条的。

4.4 看板装配与结论三态

conclusionMode触发条件含义
batch最近成功批次的范围 == 当前查询范围
且批次有 conclusion_json		 最完整：含核心事件、传播路径、舆论焦点、风险点。
derived范围不一致，或批次没存结论 由预聚合行推导的结论：只有占比、峰值桶、集中度这类统计判断， 没有核心事件与传播路径（那需要明细）。看板会显式提示口径。
none该范围尚未生成预聚合数据 返回空视图 + notice「请先执行看板重算」，不报 500。

批次失败时（BatchMeta.isDegraded()），额外下发 「最近一次聚合执行失败：{原因}，当前展示的是上一次成功聚合的结果」——这是验收 9 的落地形态。

4.5 下钻与报告交接

  • 下钻（验收 6）：DrilldownQuery.of(scope, dimType, dimKey, dimLabel, grain) → JdbcDrilldownReader 回明细表按维度条件查。八类维度 + 趋势行（趋势行按时间桶反解出时间区间）都能下钻，分页上限 maxDrilldownPageSize=200。维度类型非法返回 R.fail("不支持的维度类型")，不做静默兜底。
  • 报告交接（验收 7）：GET /handoff 返回自描述数据包 ReportSection（标题 + 指标 map + 表格块 + 结论）， F-014 报告生成直接消费，不用反向调用本模块。范围与批次不一致时，包内额外带 conclusionMode，让报告侧知道结论的成色。
  • 导出（验收 10）：POST /export 走 ExcelBuilder 输出长表（区块 / 维度 / 取值 / 数值 / 占比 / 说明）， 七类指标齐在一张 sheet —— 下游做透视比多 sheet 更顺手。

八、本轮自测抓出的两个真实缺陷

两条都是「不报错、不写日志、界面只是『没数据』」的静默缺陷 —— 人工点页面基本发现不了。

缺陷现象修法
DrilldownQuery.trendRange 的长度守卫把周桶挡在门外 守卫写的是「bucketKey.length() < 10 直接返回 null」， 而周桶键是 2026-W36，只有 8 个字符 —— 于是周粒度下钻在生产里永远返回空明细： 点趋势图上的周柱子，抽屉里什么都没有。日桶（10 字符）与小时桶（13 字符）恰好都能过，所以只坏周这一档。 把「长度 < 10 就退出」的粗粒度守卫下移到各分支内部：小时分支单独要求 ≥13， 周分支不要求长度、只要求能按 yyyy-Www 反解。同时补上 drilldownTrendRange 断言覆盖三档粒度。
表定义里重复声明了主键列 yq_stats_dim 的字段清单里手写了 L('dimId','dim_id',…)、yq_stats_hot 写了 L('hotId','hot_id',…)， 而生成器本身就会为每张表补主键列 ⇒ 产出的建表 SQL 与 TS types.ts 出现重复列 / 重复字段（vue-tsc 报 TS2300）。 从 gen-yuqing.mjs 的表定义中删掉这两行（主键交给生成器统一补）。 并在 checker 第 13 类新增两条守卫：「三份 SQL 的全部建表语句均无重复列」「PC 端 yuqing/*/types.ts 接口无重复字段」，防回归。

九、已知边界（没藏着）

  1. 未在真实 Doris 集群上跑过端到端。本机无 Doris 实例，JdbcStatsWriter / JdbcStatsQuery 的 SQL 只经过离线单测与 check-yuqing-sql.mjs 静态校验。验收 8 的「不随数据量变慢」是架构上成立，不是压测结论 —— 首次上真实环境后需要人工跑一次大数据量看板。
  2. 结论的成色取决于范围是否与批次一致。跨范围查询只能拿到「派生结论」（无核心事件与传播路径）。 F-014 报告若要用完整结论，请先按同范围重算再看交接包，或直接读批次的 conclusion_json。
  3. 小时粒度只回算最近 hourTrendDays=30 天。小时桶行数增长最快，必须封顶；更早的小时桶查不到（日 / 周不受限）。 需要历史小时曲线时手动重算并临时调大该值。
  4. 明细读取有硬上限 maxSourceRecords=200000。命中即截断，指标为不完全统计，批次 notice 与看板 notices 双处留痕， 但不会报错——必须有人看懂那条提示，否则会把截断后的数字当成全量。
  5. 口径差异是设计内的。趋势按发布时间、总量按采集日，跨日传播时「曲线累计 ≠ 总量卡片」。 看板下发 trendBase 供前端标注，但若下游系统（报告、导出）不读这个字段，就会误以为数据不对。
  6. 预聚合粒度固定为「按天 × 按任务 × 按渠道」。想按「周 × 地域」这类组合直接聚合是不支持的，只能下钻到明细或另建预聚合。 这是「表数量 vs 灵活性」的取舍，本期选了表少。
  7. 本模块不做数据行级鉴权。按需求，舆情台账对所有持权角色可见，因此仅靠 yuqing:dashboard:* 三枚权限码控制； 将来若要做「按部门 / 按任务隔离看到的统计」，需要在这里补范围条件，属新增需求，不是配置项。

十、上线步骤

  1. 执行 SQL（顺序不能反）：script/sql/yuqing/yq_schema.sql（含新表 yq_stats_batch）→ yq_doris_schema.sql 与 yq_doris_mysql_fallback.sql（3 张预聚合表，按实际数据源二选一或都执行）→ yq_dict.sql → yq_menu.sql。
  2. 导入配置：script/sql/yuqing/config/yq_analytics.yml。重点确认 trendByPublishTime（趋势口径）、hotTopN、hourTrendDays、maxSourceRecords。
  3. SnailJob 控制台新建执行器 yuqingStatsAggregate，调度周期建议 600~1800s（回看天数默认 2 天，允许失败后自愈）。
  4. 重启后端 → 进 PC「统计看板」→ 点看板重算生成首份预聚合（首次必须先手动跑一次，否则看板是空的）。
