四、引擎设计

4.1 预警引擎（AlertEngine）判定顺序

yq_opinion(Doris) ──► YqOpinionReader（回看窗口，回填渠道名）

for each 启用的预警规则（按 alert_level 降序、优先级取先命中）
  1. 场景匹配   AlertScene.parse(trigger_scenes)  命中 new_negative / high_risk / burst_increment / special_topic
  2. 分级兜底   LevelResolver   analyzeStatus≠done → 本地判级；否则用已有等级
  3. 窗口计数   AlertCountSource.count(task, channel, senti, from, to)   ← 全部走 LambdaQueryWrapper
  4. 突发判定   BurstDetector   近 7 窗口移动均值基线；cur ≥ min_burst_count 且 cur ≥ 基线 × burst_ratio
  5. 阈值比对   条数阈值 / 热度阈值 / 风险等级阈值 同时满足才算命中
  6. 指纹冷却   AlertFingerprint  同指纹在 cooldown_minutes 内已预警 → 计入重复，不再落库
  7. 落库       yq_alert（status=pending，写 trigger_rule / trigger_value / trigger_time / fingerprint）
  • 预览模式：scan(req.setPreviewOnly(true)) 走同一套判定但不落库，供 PC「预览命中」按钮在改规则前先看影响面。
  • 零命中不是异常：判定链全程 try-catch 单条规则，某条规则配置写错只降级该规则并记录原因，不中断整轮扫描。

4.2 预警状态机（AlertStatusMachine）

状态允许流转到约束
pendingprocessing / handled / ignored初始态
processinghandled / ignored处置中可不填说明
handled—（终态）必须填处置说明，服务端 + 前端双重校验（验收标准 6）
ignored—（终态）必须填忽略原因

处置人身份只从 Sa-Token 取（LoginHelper.getUserId()），请求体里带的 processBy 一律忽略，杜绝「替别人签处置」的越权。

4.3 推送引擎（PushDispatcher）流水线

pushAlerts(alertIds)
  └─ ① PushTargetResolver       角色 / 部门 / 指定人员 → 企微 userid 集合；对象级推送开关（验收 11）关掉即跳过
  └─ ② PushScene / 级别绑定      warning|urgent → immediate 即时；其余 → scheduled 定时批量（验收 4）
  └─ ③ QuietHoursGuard          免打扰判定，支持跨夜（22:00–08:00）；命中则标记 deferred 顺延，不算失败
  └─ ④ PushTemplateRenderer     immediate 走「10 要素明细模板」；scheduled 走「摘要式模板」（验收 5/6）
  └─ ⑤ 截断                    长正文按 maxContentChars 截断并保留原文链接（验收 7）
  └─ ⑥ WecomTransport           有凭据 → HttpWecomTransport（token 缓存 + 真实 HTTP）；无凭据 → 降级且记失败
  └─ ⑦ PushRetryPolicy          失败按 2000ms × 2^(n-1) 指数退避重试，上限硬编码 10；耗尽写 fail_reason
  └─ ⑧ 落 yq_push_record         对象 / 场景 / 模板 / 内容快照 / 发送时间 / 结果 / 重试次数，成败全留痕（验收 9）
  └─ ⑨ 回写 yq_alert.push_result 预警台账直接看到推送结果（验收 10）

定时批量顺延：免打扰期间不丢消息，落 deferred；由 flushScheduled() 在下一个非免打扰时段刷出 （PC 与定时任务都提供入口），保证「晚上 2 点的高风险舆情，早上 8 点一定会到人手上」。

八、自测抓出的两个真实缺陷（说明测试是有效的，不是摆设）

缺陷现象修法
applyTemplate 未清空未知占位符 模板 【{level}】{title} 链接：{url} 在 vars 里没有 url 时，企业微信里会原样出现 链接：{url} —— 既泄露内部实现，又让人以为是平台故障。 替换已知占位符后，再扫一遍把未被提供的 {xxx} 清空（单层、长度 ≤33 才认，避免误删正文花括号）。
normalizeMaxRetry 负数语义反了 -1 被当成「未配置」回落成默认 3，于是想彻底关掉重试反而重试 3 次，正好打爆企微接口限频。 负数 = 显式禁用（0 次）；0 / 缺失才回落默认值；硬上限 10 不变。

两条都是「配置看似生效、实际行为相反」的隐性缺陷，单靠人工点页面发现不了，只能靠离线断言拦。

九、已知边界（没藏着）

  1. 判级仍是兜底的：F-007 智能研判未落地，LevelResolver 用本地规则判级。F-007 落地后自动让位，但在此之前「高风险判定」的准确度受限于规则，不是模型。
  2. 企微真实链路未在真实凭据下跑通：HttpWecomTransport 已实现 token 获取、文本 / markdown / 文件上传、错误码解析，但本机无 corpId/corpSecret/agentId，实测走的是「降级记失败」分支。首次配置凭据后需人工验证一条真实下发。
  3. 验收 10 的报告文件推送只完成一半：通道与 H5 入口基址已就绪，触发方在 F-014/F-015，尚未实现。
  4. 验收 9 的短信 / 电话只留了扩展点：新通道 = 实现 WecomTransport 接口 + 加一枚 channel_type 字典值，不改流水线。本期按 PRD 要求不实际开通。
  5. 120 秒时效是「机制上满足」而非「压测过」：扫描周期 5min 的配置下，最坏情况会超 120s。生产建议把即时场景的扫描周期调到 1min，或给 urgent 级别走独立的短周期任务。
  6. 突发基线依赖 Doris 有历史数据：冷启动头 7 个窗口基线为空，此时只靠 min_burst_count 兜底，会偏向保守（宁可漏报不虚报）。

十、上线步骤

  1. 执行 SQL：script/sql/yuqing/yq_schema.sql（含 9 个新列）→ yq_dict.sql → yq_menu.sql。
  2. 导入配置：script/sql/yuqing/config/yq_alert.yml，填入企微 corpId / corpSecret / agentId 与 h5BaseUrl。
  3. SnailJob 控制台新建执行器 yuqingAlertScan，调度周期建议 60s（即时场景）或 300s（仅批量场景）。
  4. 重启后端，在 yq_alert_rule 配一条最小规则（场景 new_negative + 条数阈值 1 + 级别 warning）。
