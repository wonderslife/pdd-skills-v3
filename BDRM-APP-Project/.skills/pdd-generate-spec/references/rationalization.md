# 理性化对照表（Rationalization Table）

> 生成规格时用于自我审视、避免常见陷阱。本文件为完整参考。

## 陷阱对照表

| # | 陷阱 / Trap | 请问自己 / Ask Yourself | 应该怎么做 / Action |
|---|------------|----------------------|---------------------|
| 1 | "这个接口很简单,写个路径就行了" | 简单的接口也需要明确的参数定义,否则实现者会自行猜测 | 即使是最简单的CRUD接口也必须定义完整的请求/响应结构 |
| 2 | "验收标准差不多就行,反正后面会测" | 模糊的验收标准会导致验收阶段扯皮,且无法客观判断是否通过 | 每条标准都必须量化或提供明确的判定方法 |
| 3 | "前端后面再对吧,先完成后端" | 前后端不一致是集成阶段最常见的问题 | 规格生成时就必须同步考虑前后端,确保接口定义的双向适用性 |
| 4 | "这些细节实现者应该知道" | 不同开发者有不同的理解和习惯,细节缺失会导致实现差异 | 将你认为"显而易见"的细节都显式写入规格,特别是边界条件 |
| 5 | "规格写得太长没人看" | 过于简略的规格会导致频繁沟通,反而浪费更多时间 | 采用分层详略策略:概览+详细表格,让读者可按需深入 |

## 常见陷阱

1. **"假 completeness"陷阱**: 看起来覆盖了所有章节但每章内容空洞 → 建立"章节质量检查":每章至少回答What/Who/How三个问题
2. **"主观验收"陷阱**: 使用无法客观验证的描述作为验收标准 → 强制要求每条标准可通过自动化测试或明确步骤验证
3. **"后端偏见"陷阱**: 规格只关注后端实现而忽略前端需求 → 强制要求规格包含"前端适配"章节,明确Vue组件需要的数据结构
4. **"快照思维"陷阱**: 将规格视为静态文档而不考虑变更管理 → 在规格模板中内置CHANGELOG区域,鼓励记录变更历史
