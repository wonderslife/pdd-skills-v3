# 领域预设：融媒体 / 内容发布平台

> 适用：融媒体发布平台、CMS、内容中台、稿件生产与分发系统。
> 使用方式：**改写，不是照抄**。把状态枚举、渠道列表换成你项目 PRD 里的真实值。
>
> 本预设的状态与渠道取值来自 `project/Converged-Publishing-Platform` 的真实 PRD 与 dev-specs，
> 可直接作为同类项目的起手基线。

---

## 一、为什么融媒体平台需要独立预设

三个别的系统没有的结构性特征：

1. **状态机长**：一条稿件从采集到发布要经过 8-12 个状态，且存在"驳回"的多分支（退回修改 vs 退回重写）
2. **渠道维度**：同一条稿件要发到 6-10 个平台，每个平台独立成败 → 产生"部分成功"这种复合状态
3. **内容分级**：涉政/涉密内容有强制人工审核通道，必须在 UI 上可辨识

这三条决定了：**通用的 3 色状态板（红黄绿）完全不够用**，必须有专门的状态体系设计。

## 二、稿件状态机色板

### 状态全集

| # | 状态 | Token | 色值 | 图标 | 文案 | 可编辑 | 可发布 | 谁可操作 |
|---|------|-------|------|------|------|--------|--------|---------|
| 1 | 草稿 | `state-draft` | #86909C | ○ | 草稿 | 是 | 否 | 创建人 |
| 2 | 待审核 | `state-pending` | #FF7D00 | ◔ | 待审核 | 否 | 否 | 编辑可撤回 |
| 3 | 审核中 | `state-reviewing` | #0F2A8C | ◑ | 审核中 | 否 | 否 | 审核员 |
| 4 | 已通过 | `state-approved` | #00B42A | ✓ | 已通过 | 否 | 是 | 编辑/发布员 |
| 5 | 驳回-修改 | `state-returned` | #F53F3F | ↩ | 退回修改 | 是 | 否 | 创建人 |
| 6 | 驳回-重写 | `state-rewrite` | #A8071A | ↻ | 退回重写 | 否 | 否 | 创建人触发 AI |
| 7 | 定时待发 | `state-scheduled` | #722ED1 | ◷ | 定时待发 | 是 | 否 | 编辑 |
| 8 | 已发布 | `state-published` | #237804 | ● | 已发布 | 否 | — | 仅可撤回 |
| 9 | 部分成功 | `state-partial` | #08979C | ◐ | 部分成功 | 否 | — | 发布员重试 |
| 10 | 发布失败 | `state-failed` | #AD4E00 | ⚠ | 发布失败 | 否 | — | 发布员重试 |
| 11 | 已撤回 | `state-withdrawn` | #595959 | ⊘ | 已撤回 | 是 | 否 | 编辑 |

### 色族结构（8 族承载 11 态）

11 个状态**不要**各占一个色相——色相距离会挤到 15° 以内，反而更难分。正确做法是收敛色相，用**明度差（≥18）+ 图标**承担细分：

| 族 | 状态 | 区分手段 |
|----|------|---------|
| 灰 | 草稿 / 已撤回 | 明度 + 图标 |
| 橙 | 待审核 | 色相 |
| 深橙 | 发布失败 | 同族，明度差 24 + ⚠ |
| 深靛 | 审核中 | 与品牌蓝同系但更深（L 22 vs 46） |
| 绿 | 已通过 / 已发布 | 明度差 22 + 图标（✓ / ●） |
| 红 | 退回修改 / 退回重写 | 明度差 21 + 图标（↩ / ↻） |
| 紫 | 定时待发 | 色相 |
| 青 | 部分成功 | 色相 |

### 状态色只作圆点，不作文字（关键）

**不要**用"彩色文字 + 浅色背景"做状态标签。高明度橙/绿做 12px 文字必然对比度不足（#FF7D00 在白底仅 2.57:1，#00B42A 仅 2.78:1，远低于 WCAG 4.5:1）。

正确做法：

```html
<span class="status"><i class="dot dot--returned">↩</i>退回修改</span>
```
```css
.status { display:inline-flex; align-items:center; gap:4px;
          font-size:12px; color:var(--ink-body); }   /* 7.2:1 */
.dot { width:14px; height:14px; border-radius:2px;
       display:inline-flex; align-items:center; justify-content:center;
       font-size:10px; color:#fff; }
.dot--returned { background: var(--state-returned); }
```

**原理**：颜色只需要在 14px 色块内被**识别**，不需要被**阅读**。这一条同时解决可读性、色盲、黑白打印三个问题。

### 三个关键设计决策

**决策 1：驳回必须分两支**

"退回修改"和"退回重写"是**完全不同的下游动作**：

- 退回修改 → 编辑手工改稿 → 重新提审
- 退回重写 → 系统重新触发 AI 生成 → 保留原版本

如果用同一个"已驳回"状态，编辑打开稿件时不知道该干什么。必须两个状态、两个明度（#F53F3F / #A8071A）、两个图标（↩ / ↻）。

> 这条是融媒体平台最容易做错的地方：状态数量看起来"太多想合并"，但合并的代价是用户每次都要点进详情才知道下一步做什么。

**决策 2：已通过 ≠ 已发布**

- 已通过（#00B42A）是**审核终态**
- 已发布（#237804）是**分发终态**

两者都是绿，但明度不同（#00B42A vs #237804），且图标不同（✓ vs ●）。合并会导致"审核队列里分不清哪些还没发出去"。

**决策 3：必须有"部分成功"**

F-502 明确要求"各平台独立返回发布结果，互不影响"。所以一条稿件发 8 个平台，可能 6 成 2 败——这个状态既不是成功也不是失败，必须独立。

**"部分成功"是融媒体平台区别于普通 CMS 的核心状态**，也是列表页最需要快速定位的状态（运营要找出"哪些稿件还差几个平台没发出去"）。

## 三、渠道状态（子状态体系）
稿件是父状态，"部分成功"之下需要展示每个渠道的子状态。

### 渠道清单（按项目实际增删）

| 渠道码 | 名称 | 类型 | 特殊要求 |
|--------|------|------|---------|
| `WEB` | 网站 | 自有 | 无 |
| `APP` | 客户端 | 自有 | 需推送到消息中心 |
| `WECHAT_MP` | 微信公众号 | 三方 | 需素材上传、有图文条数限制 |
| `WECHAT_VIDEO` | 视频号 | 三方 | 仅视频 |
| `WEIBO` | 新浪微博 | 三方 | 字数限制、图片数量限制 |
| `DOUYIN` | 抖音 | 三方 | 仅视频、需审核 |
| `KUAISHOU` | 快手 | 三方 | 仅视频、需审核 |
| `BAIJIAHAO` | 百家号 | 三方 | 需审核 |
| `TOUTIAO` | 今日头条 | 三方 | 需审核 |

### 渠道子状态表达

```html
<!-- 详情页「分发状态」区块 -->
<ul class="channel-grid">
  <li class="channel is-success">
    <span class="ch-code">WEB</span>
    <span class="ch-name">网站</span>
    <span class="ch-status"><i>✓</i>已发布</span>
  </li>
  <li class="channel is-failed" title="失败原因：access_token 过期">
    <span class="ch-code">WECHAT_MP</span>
    <span class="ch-name">微信公众号</span>
    <span class="ch-status"><i>⚠</i>失败 · 重试 2/3</span>
  </li>
</ul>
```

**规则**：
- 渠道码用等宽字体（`mono-tag`），便于逐字比对
- 每个渠道必须显示"重试次数/上限"，否则运营不知道还能不能重试
- 失败渠道的 tooltip 必须给失败原因原文，不给"发布失败"这种废话

## 四、内容分级标识（合规）

涉政、涉密、敏感内容有强制人工审核通道，必须在 UI 上可辨识。

| 级别 | Token | 标识 | 规则 |
|------|-------|------|------|
| 普通 | 无 | — | 可走自动审核 |
| 关注 | `flag-attention` #FAAD14 | ▲ 关注 | 建议人工复核 |
| 敏感 | `flag-sensitive` #D4380D | ▲ 敏感 | 强制人工审核，禁止自动放行 |
| 涉政 | `flag-political` #A8071A | ⬤ 涉政 | 强制人工 + 双人复核，禁止自动放行 |

**实现要求**：
- 标识必须出现在**列表页**（不能只在详情页），否则审核员无法批量识别
- 涉政标识不可通过任何前端操作隐藏
- 标识颜色与状态色板分离（用 `flag-*` 前缀，不与 `state-*` 混）

## 五、栏目色彩体系

栏目是融媒体平台的核心组织维度。给每个栏目分配固定色，前后台共用。

```js
// 存栏目表，不存前端常量
// channel: { id, name, slug, color }
const CHANNEL_COLORS = {
  politics:  '#C8102E',  // 时政
  economy:   '#165DFF',  // 财经
  society:   '#00B42A',  // 社会
  culture:   '#722ED1',  // 文化
  sports:    '#FF7D00',  // 体育
  tech:      '#0FC6C2',  // 科技
  local:     '#86909C',  // 地方
};
```

**用法**：
- 前台栏目页标题前的色条
- 后台稿件列表的栏目标签（左侧 3px 竖条 + 栏目名，不用整块底色——整块底色会与状态标签抢注意力）
- 导航当前栏目指示

**规则**：
> 栏目色只做识别，不做状态。栏目色不得与 `state-*` 任一色相距离 < 25°。

**注意**：栏目色数量会增长，必须定义"超出预置色后的分配策略"（如按 HSL 色相均分），否则新增栏目会撞色。

## 六、直播/实时子系统

融媒体平台的直播场景独立于稿件状态机。

| 组件 | Token | 说明 |
|------|-------|------|
| 直播徽标 | `live` #E8352D / `live-bg` #FFF1F0 | 脉冲圆点 + "直播中" |
| 快讯通栏 | `live` 满幅底色 + 白字 | 页面顶部通栏，仅重大事件用 |
| 时间轴节点 | `live` 圆点 + `hairline` 竖线 | 直播图文流 |
| 在线人数 | `live` + `mono-tag` | 等宽数字，实时跳动用 `tabular-nums` 防抖 |

**规则**：
> `live` 与 `state-*` 完全隔离。直播中的稿件，其稿件状态仍是"已发布"——实时是另一维度，不是状态。

## 七、内容模型 → 模板映射

融媒体平台的核心复杂度：不同内容类型字段不同、审核路径不同、可发渠道不同。

| 内容类型 | 必填字段 | 专属字段 | 可发渠道 | 审核路径 |
|---------|---------|---------|---------|---------|
| 图文稿 | 标题/正文/栏目/作者 | 封面图、摘要、标签 | 全渠道 | 常规 |
| 视频稿 | 标题/视频/栏目 | 时长、封面、字幕 | 视频类渠道 | 常规 + 内容抽帧 |
| 图集 | 标题/图片≥3/栏目 | 图片说明、版权 | WEB/APP/微博/百家号 | 常规 |
| 快讯 | 标题/正文≤200字/栏目 | 关联事件ID | WEB/APP/微博 | 快速通道 |
| 专题 | 标题/栏目/子稿件列表 | 排序、模板样式 | WEB/APP | 主编审批 |
| 直播 | 标题/推流地址/栏目 | 开始时间、主播 | WEB/APP/视频号 | 主编审批 |

**设计含义**：
- 列表页需要"类型"列（用 `mono-tag` 显示 `ARTICLE` / `VIDEO` / `GALLERY` / `FLASH`）
- 新建时必须先选类型再进表单（不同类型表单不同）
- 分发配置页必须按类型过滤可选渠道（视频稿不能选微博图文位）

## 八、AI 标注的展示规范

F-301 要求"审核页面同屏展示正文与 AI 标注（标注点、问题类型、置信度）"。这是融媒体平台特有的 UI 模式。

### 布局

```
┌─────────────────────────┬──────────────┐
│                         │  AI 标注列表  │
│      正文（可滚动）       │  ─────────   │
│   ┌ 高亮片段 ┐            │  ⚠ 敏感词    │
│   │          │            │  置信度 92%  │
│   └──────────┘            │  [定位][忽略]│
│                         │  ─────────   │
│                         │  ⚠ 事实存疑  │
│                         │  置信度 67%  │
└─────────────────────────┴──────────────┘
```

### 置信度分档（必须有视觉区分）

| 档位 | 阈值 | 表达 | 交互 |
|------|------|------|------|
| 高 | ≥85% | `state-failed` 红 + 实线高亮 | 必须处理才能通过 |
| 中 | 60-85% | `state-pending` 橙 + 虚线高亮 | 建议处理 |
| 低 | <60% | `ink-subtle` 灰 + 点状下划线 | 仅提示 |

**规则**：
> 置信度用分档而非精确数字做主要视觉表达。审核员不需要"92.3%"，需要"这个必须看"。

**联动要求**：
- 点击标注列表项 → 正文滚动定位 + 高亮闪烁一次
- 点击正文高亮片段 → 右侧标注列表定位
- 双向联动是硬要求，单向等于没有

## 九、本预设的 Do's / Don'ts

### Do
- 驳回必须分"退回修改"与"退回重写"两态
- 状态色只作 14px 圆点，标签文字用中性深灰（`ink-body`）
- 已通过与已发布必须两态（同色系不同明度）
- 必须有"部分成功"状态 + 每渠道子状态 + 重试次数
- 内容分级标识必须出现在列表页
- 渠道码、稿件 ID、时间戳一律等宽字体
- 栏目色只做识别，不与状态色混
- AI 置信度用分档而非精确百分比做主视觉

### Don't
- 不要把 11 个状态压缩成 4 个（用户每次都要点进去才知道下一步）
- 不要用状态色作 12px 文字（对比度必然不足）
- 不要用"发布失败"覆盖"部分成功"
- 不要让 `live` 与 `state-*` 共用色值
- 不要用整块底色做栏目标签（会与状态标签抢注意力）
- 不要在列表页隐藏涉政/敏感标识
- 不要让渠道失败原因显示为"发布失败"（必须给原文）

## 十、迁移到其他内容平台的改法

本预设的核心结构可迁移，只需替换三处：

| 要素 | 融媒体 | 电商内容 | 企业知识库 |
|------|--------|---------|-----------|
| 状态机 | 采集→待审→审核→通过→分发 | 草稿→待审→上架→下架 | 草稿→待审→发布→归档 |
| 渠道维度 | 网站/APP/微信/抖音… | 淘宝/京东/抖音小店 | 内网/企微/公众号 |
| 分级维度 | 涉政/涉密 | 品牌合规/类目资质 | 保密等级 |

**保持不变**的：状态双编码、驳回分支、部分成功、列表页分级标识、等宽技术标签。
